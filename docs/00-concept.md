# 00 — Concept & Architecture

Design authority for BajaOvrLay. This file is authoritative between milestones: as-built changes are written into it in the PR that makes them. The Plane page of the same name (BAJAOVRLAY project, `personal` workspace) is the human-readable mirror, which João updates from this file at each milestone close. v0.1 rev 3 plus decision records §18–§19.

## 1. What this is

A stream-graphics system for Baja SAE Brasil live streams: an operator control page where graphics are configured, pre-programmed and queued, and a renderer page that OBS loads as a browser source and that plays the graphics on air. Graphics get their data from the Baja scoring system, from small databases we run ourselves (teams, people, sponsors, schedule), and from values typed in by hand.

The previous attempt failed on three fronts (functionality, control, looks), so this project starts from a written design and treats operator usability as the primary requirement. A stream at the track is run by volunteers under time pressure; anything that needs explanation on the day is a defect.

### Non-goals for v1

- A visual template editor. Graphics are authored in code by a developer; operators only fill fields and press buttons.
- CasparCG or SDI output, newsroom (MOS) integration, 24/7 unattended playout.
- Multi-tenant or public hosting. This runs on our LAN at the event and on TrueNAS between events.

## 2. Vocabulary

- Graphic: one on-screen element type (clock, lower third, standings table), packaged as an EBU OGraf graphic: a manifest, a web component and assets.
- Layer: a named slot in the output where at most one graphic instance is on air at a time (clock, lower-third, fullscreen, ticker, bug). Layers have a fixed z-order.
- Item: a prepared use of a graphic: which graphic, which layer, and a value or a binding for each field. Items live in a rundown or in a quick-fire panel.
- Binding: a field value looked up from a data source instead of typed (for example scoring.enduro.positions). A binding is either live (keeps updating while on air) or a snapshot (frozen at take).
- Rundown: an ordered list of items for a session, with a cursor for "next".
- Take, Clear, Next: put an item on air on its layer; remove what is on that layer; advance a multi-step graphic (or the rundown cursor).
- Preview: rendering an item off-air so the operator can see it before taking it.
- Instance: a graphic currently loaded in the renderer (previewing or on air), with the data it was resolved with.
- Data source: a poller that produces a normalized JSON snapshot: scoring, a sheet or CSV, the entity library. (Original wording; the data words as built in M2 are below.)
- Entity: a record in our own library: team, person (speaker, judge), sponsor, schedule slot.
- Macro: a named list of commands run as one button press (clock on, positions on, bug on).

The words as João confirmed them after the M1 walk (BAJAOVRLAY-36), and as the control page uses them:

- Graphic (gráfico): one installed OGraf package, the race clock for example; it has a schema and no data of its own.
- Item: a saved use of one graphic on one layer with its field values, kept for the next takes; its graphic never changes, its layer and values do.
- Rundown: the ordered list of items of a session, with the cursor on the next one.
- Shortcut panel (painel de atalhos): a tab of buttons in "Atalhos e macros"; each button is an item, taken ad hoc, never moving the cursor.
- Instance: one graphic on an output right now, on air (program) or in preview, with the data it shows; taking or previewing an item makes one, and it names that item.
- Layer (camada): a slot of the output, in z-order, holding at most one instance per output.
- Macro: a list of steps (take an item, clear a layer, clear all, wait) run in order by one press.
- Preview (prévia): the result, exactly what the screen will look like after the take: what is previewed, what stays on air, and the layers marked "vai limpar".
- "Editar item" changes an item, and so every take of it from then on; "Edição rápida" changes one instance, the one loaded with "Editar" from a Camadas row, and that change is a one-off ("alterado no ar") until the operator saves it into the item ("Salvar no item").

Everything on air or in preview comes from an item (BAJAOVRLAY-37). Items are what can go on air; "Edição rápida" only changes what is already up, and a graphic made on the spot is made as a new item ("Novo gráfico…", then "Salvar e disparar").

The data words as built in M2 (BAJAOVRLAY-17), and as the "Fontes de dados" page uses them:

- Canonical shape (forma canônica): what session, positions, standings or brackets look like inside BajaOvrLay (packages/shared/src/dataShapes, §8). Every source maps its data into these four, and graphics bind only to them, never to a source's own format.
- Data source (fonte de dados): something the server polls for race data, one of a few kinds; the server keeps its last good answer (its snapshot) and says whether it is late ("atrasada"). An adapter is the code that reads one kind of source and answers a poll with canonical shapes.
- Simulator (simulador): a source that produces a deterministic Baja enduro from a seed and the time since its start, so graphics are built and rehearsed with nobody typing data. Its teams are fictional and its scoring is not the real one.
- Recording (gravação) and replay (reprodução): a recording is a source's good answers written to a file while "Gravar" is on; a replay is a source that plays a recording back on today's timeline. A rehearsal is a show run against a replay (§7 rule 8).

The data words added by BAJAOVRLAY-40:

- Flex source (fonte flexível, kind httpJson, "HTTP/JSON (flexível)" on the page): one adapter for any JSON API. Its config says which addresses to read (GET only) and how their JSON maps into the canonical shapes; after that it is a source like any other (polled, stale-marked, recorded, replayed). The Baja app source (BAJAOVRLAY-18) is a configuration of this kind.
- Mapping (mapeamento): the declarative part of a flex source's config. For each shape it produces, the request it reads and one rule per canonical field: a path in the response, a fixed value, the place in the list or the moment of the poll, with at most one transform. Never an expression, a template or user code (architecture rule 5).
- Transform (transformação): a named, pure function of the registry (packages/shared/src/transforms) that turns one value, "4:38.293" into 278 293 ms for example. It answers the new value or a pt-BR reason quoting the value it could not read, and never throws.

The data words added by BAJAOVRLAY-20, as the item editor, "Edição rápida", Camadas and "Fontes" use them:

- Binding (vínculo, "Fonte" in the item editor): an item field that reads its value from a data source instead of holding a typed one: which source, which canonical shape, which path in it (one the picker lists, packages/shared/src/dataShapes/bindablePaths.ts), and at most one binding transform. A path may follow a car chosen by its number (Posições › Carro escolhido pelo número › …) instead of a place.
- Live and snapshot (ao vivo, congelado na entrada): a live binding keeps updating while its instance is on air or in preview; a snapshot binding is read once, at the take (for a preview, again at "Tomar": frozen at the take, not at the preview).
- Override (correção, "Corrigir valor…", "Corrigir valor da fonte…"): an operator-typed value that wins over what one source says, everywhere that source is bound, until it is removed ("Remover correção"). It corrects a session field, or one field of one car wherever the car is listed, never a place.
- Clock group (relógio completo, "Relógio da fonte"): the source's whole session clock read as one binding, which fills a graphic's four clock fields (roles clockTime, wallClock, clockRunning, clockMode) at once, so a clock never shows a new time with an old moment.

The words added by BAJAOVRLAY-44, as the "Eventos" tab and "Regras" use them:

- Event (evento): something that happened once and should appear once, as opposed to state, which a graphic follows: a penalty given (an incident id a source lists for the first time), a new fastest lap, a change of leader, a notice the operator types, later a viewer's Super Chat. Each has a deterministic id, built from what happened, never from when, so it is listed once even across a restart.
- Inbox (caixa de eventos, the console's "Eventos" tab and the "Eventos" page): the server's list of events, each pending (waiting for the operator), queued (waiting for its layer, to go on air by itself), on air, shown, dismissed or expired.
- Rule (regra): one per kind of event: ask the operator, go on air by itself, or ignore; the prepared item that shows it, how long it stays on air, and how long it may wait before it expires. A Super Chat's rule can only ask.
- Item filled by an event (template): an item whose fields read the event it shows ("Evento" in the item editor); it goes on air only through an event, never by a take of its own.

The words added by BAJAOVRLAY-19, as the "Cadastros" page and the item editor use them:

- Entity library (cadastros): our own small tables, kept on "Cadastros" or imported from CSV: teams (equipes, each keyed by its car number, the key of the positions), people (pessoas), sponsors (patrocinadores) and the day's schedule (programação, whose status, concluída, em andamento or a seguir, is worked out from the clock and never stored). An entity is one record of it.
- Entity reference ("Cadastro" in the item editor): an item field that reads one attribute of one record of the library (the team name of car 7, the logo of car 42), always live: an edit in Cadastros reaches the air by itself.
- Media (imagens): the logos and photos of the library, uploaded to the server and named by the SHA-256 of their bytes (the media id); a resolved image field holds the image's address, /media/<mediaId>.

## 3. Architecture

Four deployable parts, one repository, one Node process at runtime.

- Control page (browser) talks to the server over WebSocket and REST.
- Server (Node) holds the state store (in memory, persisted to SQLite), the data sources (pollers producing snapshots), the binding resolver (item fields plus snapshots become data for a graphic), OBS control (obs-websocket) and the REST API at /api/v1 with OpenAPI, used by Companion, Stream Deck and scripts.
- Renderer page (browser inside OBS) receives state from the server over WebSocket.
- Graphics (OGraf packages) are static files served by the server and loaded by the renderer.

### 3.1 The server owns the truth

The server holds the whole application state in memory and persists it to SQLite. Clients never hold state of their own; they send commands and receive state. Every command that changes something or is refused is appended to an event log (who, when, what), with one exception since BAJAOVRLAY-17: a routine data-source poll that leaves the source's health as it was writes no row (§4). This is the NodeCG "replicant" idea reimplemented in one module: a store of named slices, each validated by a Zod schema, each broadcast to every connected client when it changes (the slices of one change together, in one message, §4). dataSnapshots is the one exception: after the hello, its changes travel source by source in the dataSnapshot message, to operator connections only, and screen connections (renderer and monitor) receive only the slices they draw, layers, graphics, instances and previewClearedLayerIds, every other slice (instanceBindings and overrides included) reaching them as an empty list (§4). Since BAJAOVRLAY-20 a routine refresh of bound fields writes no event-log row either (§4).

Consequences:

- A control page refresh loses nothing.
- A renderer refresh (OBS reloading the browser source) re-requests the snapshot and rebuilds exactly what was on air.
- Two operators on two devices see the same thing at the same time.

### 3.2 The renderer is thin and dumb

A framework-free TypeScript page. One absolutely positioned container element per layer, stacked in z-order. It loads OGraf graphics as ES modules and drives them through the OGraf lifecycle (load, playAction, updateAction, stopAction, dispose). It has no logic about what to show; it mirrors the instances slice. Every dependency in the renderer is a frame-drop risk inside OBS, so it stays minimal.

### 3.3 Graphics are OGraf, nothing else

Each graphic is an OGraf v1 package with a JSON Schema for its data. That schema is what the control page uses to generate the item form; no hand-written form per graphic. Graphics receive resolved data only and never fetch anything themselves. Theme values (colors, fonts, logos) arrive as CSS custom properties that the renderer sets on the layer container.

As built in M1 (BAJAOVRLAY-14): the control page holds no code for any one graphic, and a test (apps/control/src/noGraphicSpecificCode.test.ts) fails if the race clock's id or its reference field is named outside the catalog and the tests. Both forms, the item editor's and "Edição rápida", are generated by features/schemaForm from the manifest's schema, which must be an object with properties. What it reads from each property: title is the label (the key when there is none), description the help text, default the starting value, required whether blank is refused, minimum, maximum, minLength and maxLength the limits. A string is a text input, with enum a dropdown whose option labels come from OGraf's gddOptions.labels (the enum value itself when there is none), with format date-time a date and time input sent as ISO 8601 text. An integer or number is a number input, with v_baja.unit ms a duration typed as mm:ss. A boolean is a switch. An integer with v_baja.role wallClock also offers the kind "Momento da entrada no ar" (takeTime), and starts on it in a new form. Every other shape (arrays, nested objects, oneOf and the like) is shown as read-only JSON and passed through untouched. The form checks itself with a Zod schema built from the same JSON Schema, for pt-BR messages that name the field; the server's check stays the authority. On the manifest itself the server, not the control page, reads v_baja.updateRule: the name of the rule every update of that graphic on air runs through (§4); the race clock names carryClockForward, and a graphic that names none has no rule. packages/graphics/README.md states the same for whoever writes a manifest.

As built in M2 (BAJAOVRLAY-22): the theme is a workspace package, packages/theme, holding the Ardósia tokens (packages/theme/ardosia/tokens.css, the source of truth; the design record under docs/design is read by no product code), the self-hosted Bebas Neue (fonts/fonts.css, SIL OFL) and the white logo. The server serves that folder at /theme/ (ardosia/, fonts/ and brand/ only; tokens.css and fonts.css never cached, the font file and the logo for a year), and the renderer page links the tokens and the font CSS in its head, before its script, so the custom properties are on :root and the face registered before the first graphic loads; a renderer whose :root has no token logs one error and goes on, nothing is blanked. A graphic reads every colour, size, face and duration as a CSS custom property inside its shadow root and carries no fallback value; its GSAP timelines read the --motion-* and --ease-* tokens through readMotionTokens() and register the cubic-bezier curves with GSAP's CustomEase; a guard test (packages/theme/src/noHardCodedValues.test.ts) fails on any hex colour or px font size in a graphic's source. The theme values are therefore set on the page's :root, which every layer container inherits, not on the container as this section first said.

As built in M2 (BAJAOVRLAY-19), images are assets, not data. A graphic still fetches no data (rule 3): an image field (a string the manifest marks v_baja.role imageUrl) receives the image's address, /media/<mediaId>, already resolved, and the graphic draws it with <img src>, as it loads its own fonts and its bundled logo. An <img> runs no script, even for an SVG, and the server serves every image with Content-Security-Policy default-src 'none'; style-src 'unsafe-inline'; sandbox and X-Content-Type-Options nosniff, so an SVG opened at its own address runs nothing either. A record with no image leaves an optional image field out, so the graphic must draw a finished "no image" state.

### 3.4 The control page is a realtime console

React with shadcn/ui, fully client-rendered, fed by the WebSocket state stream. Three areas always visible on a desktop layout: rundown (left), preview and program monitor (center), quick-fire panel and layer status (right). Data-operator screens (entities, standings overrides, data-source health) are separate routes that work on a tablet. As built in M2, "Fontes de dados" is #/fontes, and the console's header link and data-sources chip open it in a new tab, so the console never unmounts under the producer (gate 2 of PR #16, João). "Cadastros" (the entity library, BAJAOVRLAY-19) is #/cadastros, opened from the header's "Cadastros" in a new tab the same way, and laid out for a tablet: one tab per kind of record, its table, and the form or the CSV import in a side panel that sits under the table on a narrow screen.

## 4. State model

Slices, each a Zod schema in packages/shared. Field names below are the real ones to be used in code.

layers: id, name, zIndex, replacePolicy (one of out-then-in, cut, crossfade), persistent. Fixed list per theme; not operator-editable. As built in M2 (BAJAOVRLAY-22): the fixed layers are bug 10, ticker 20, clock 30, tower 35 ("Torre": the positions tower, under the clock on the same right-hand column, persistent like it), lower-third 40 and fullscreen 50; a layer added to the seed after a database was first seeded is added to that database at boot, so an existing installation gets the tower without a new database. Since BAJAOVRLAY-44 there is a seventh, notice 45 ("Aviso"), between the lower third and the fullscreen, not persistent, added the same way. The layer plan as built (BAJAOVRLAY-24): bug (nothing built yet), ticker (nothing yet), clock (race clock), tower (positions tower), lower-third (lower third "Tarja" and team card, so they replace each other), notice (fastest lap and penalty notice) and fullscreen (standings).

graphics: installed OGraf manifests plus our metadata: id, manifest, defaultLayerId, category, thumbnailUrl, defaultFields.

rundowns and items: Rundown has id, name, sessionLabel, cursorItemId. Item has id, home (a rundown or a quick-fire panel), order, graphicId, layerId, fields (a map from field key to FieldValue), autoOutAfterMs (optional), label, color, notes.

As built in M1: rundowns and items are two slices, persisted like the others. cursorItemId is the id of the "next" item or null. A rundown may also carry wasLastItemTakenAtCursor: the server sets it when the last item is taken at the cursor (the cursor is then on nothing because the rundown was played to its end) and takes it off as soon as the cursor is put on an item; left out means no. One rundown, "Sessão principal" (id sessao-principal), is seeded on the first boot and on a database that has none. Every item has a rundownId; quickFirePanelId arrives with the quick-fire panels. order is counted from 0 and the server keeps each rundown's orders as 0, 1, 2 and so on with no gaps. color is one of six semantic names (neutral, info, success, warning, danger, highlight). autoOutAfterMs is a whole number of milliseconds above zero; no auto-out is said by leaving it out.

FieldValue is one of:

- literal: kind 'literal', value
- binding: kind 'binding', sourceId, path, live (boolean), transformId (optional) (as built by BAJAOVRLAY-20: below)
- entity reference: kind 'entity', entityType, entityId, attribute (sugar for a binding into the entity library) (as built by BAJAOVRLAY-19: a team chosen by carNumber, not an entityId; below)

- take time: kind 'takeTime', no value (added in M1 by BAJAOVRLAY-13)

As built in M1 the FieldValue schema is a discriminated union on kind with two members. literal carries a value that may be anything, null included, but must be present. takeTime carries nothing else (one written with a value is refused, not stripped): at the take the server resolves it to the wall-clock milliseconds of that take, the same moment as the instance's takenAt and the event-log ts, and the stored item keeps saying takeTime, so every take of the item stamps its own moment. The item editor stores a wall-clock field (an integer whose manifest property says v_baja.role wallClock, such as the race clock's referenceWallClockMs) this way for every new item, so a clock saved running counts from the take and not from the save; the operator may switch the field to a typed number. What the editor stores, as built by BAJAOVRLAY-14: one FieldValue per field of the generated form, literal for a typed value and takeTime for a field left to the server; a field left cleared is not stored for a new item, and clearing a field of a stored item stores a literal null (updateItemFields cannot remove a key), which the take then leaves out of the data. The resolver stays pure: it is handed the moment of the command and reads no clock. binding and entity reference join the union in M2. Until then a field of any other kind never reaches a take: a command carrying one is refused with INVALID_COMMAND by the command schema, and a stored items row holding one stops the boot. The resolver's own refusal, UNSUPPORTED_FIELD_KIND with a message that names M2, is a guard kept ready for M2; it cannot be reached through the server today, and literal and takeTime never get it.

As built by BAJAOVRLAY-20, binding is the third member (packages/shared/src/bindings/bindingFieldValue.ts), a strict object: kind 'binding', sourceId, shapeKey (session, positions, standings or brackets), path (a path listBindablePathsOfShape lists for that shape), carNumber (only with a path under entryOfCar., which reads the car of that number wherever it is listed), isLive, and optionally transformId and transformParameters (one binding transform). The schema checks the shape only; findProblemInBinding (shared) checks that the path is listed, that a car path has its number and no other path has one, and that the transform exists, is a binding transform, reads the path's value type and has good parameters. Every bindable path carries a value type (text, integer, number, boolean, stateEnum for the flag, positionsEntries, standingsEntries, standingsScoreParts (the standings' scoreParts, since BAJAOVRLAY-24), bracketsRounds, and clockGroup for the whole session clock, the path clock), and a field takes the types its JSON Schema type allows (string: text and stateEnum; integer: integer; number: integer and number; boolean: boolean; array: the five whole lists, each only when its elements always carry every key the field's items.required names, since gate 2 of PR #25 (listItemKeys.ts); object: nothing), the clock group only on the field with the role clockTime of a graphic that marks all four clock roles. createItem and updateItemFields refuse, with INVALID_BINDING and a pt-BR message that starts with the field's title, a binding to a source that does not exist, one whose parts make no sense, one whose value (after its transform) does not fit the field, and a whole clock beside a value on one of the three other clock fields (they must hold nothing or a literal null; a takeTime there would stamp the take's moment over the source's). Stored items holding bindings load at boot, and UNSUPPORTED_FIELD_KIND now guards only entity, which arrives with the entity library (BAJAOVRLAY-19).

As built by BAJAOVRLAY-19, entity is the fourth member (packages/shared/src/entities/entityFieldValue.ts), one strict object per kind of record: kind 'entity', entityType team with carNumber, person with personId, sponsor with sponsorId or scheduleSlot with slotId, and attribute. It has no isLive: a reference is always live. The attributes are hand-listed per kind (entityAttributes.ts), each with a pt-BR label and a value type, text, integer, boolean or imageUrl: a team's carNumber, teamName, schoolName, schoolFullName, city, state, logoUrl, carPhotoUrl and logoOnLightPlate (boolean, since BAJAOVRLAY-24); a person's name, role, carNumber and photoUrl; a sponsor's name, tier, rollWeight, logoUrl and logoOnLightPlate (boolean, since BAJAOVRLAY-23); a slot's sessionName, sessionKind, startsAtMs, endsAtMs and place (its status is not one, since nothing refreshes the air when only time passes). An image attribute resolves to /media/<mediaId>. A field takes the value types its schema allows: a string marked v_baja.role imageUrl takes images only, any other string text (none when it has an enum, such as the flag), an integer or number whole numbers, a boolean a yes or no (shown to the operator as "Sim" or "Não"), anything else nothing. createItem and updateItemFields refuse, with INVALID_ENTITY_REFERENCE and the field's title first, an attribute the kind does not have, one that does not fit the field, and a record not in the library now; an optional attribute the record lacks may be saved. UNSUPPORTED_FIELD_KIND stays as the guard for a kind the schema accepts before the resolver has its case.

As built by BAJAOVRLAY-23, a literal may be a list of texts typed in the item form: a manifest property of type array whose items are plain type string (no enum, no format) is drawn line by line (one text input a line, "Adicionar <linha>" named after items.title, "Remover" and a drag handle per line), and is checked against items.minLength and items.maxLength (naming the line, "Mensagem 2: no máximo 50 caracteres (tem 80).") and the list's minItems and maxItems before anything is sent; the server's check of the manifest's schema stays the authority. It is stored and sent as the list of texts (each trimmed), so "Salvar item", "Atualizar no ar" and "Edição rápida" treat it like any field. Such a list is always typed: it offers no "Fonte" and no "Cadastro". A list of objects stays read-only, or reads a whole list from a source.

The item and rundown commands, as settled by BAJAOVRLAY-13: createItem (rundownId, graphicId, layerId, fields, label, and optionally order, color, notes, autoOutAfterMs) puts the item at the end of the rundown, or at the given position with the items from there on moving down by one; the server makes the id. updateItemFields (itemId, and any of fields, label, color, notes, autoOutAfterMs) changes only what it carries: fields are merged key by key, autoOutAfterMs null removes the delay, and the rundown, graphic and layer of an item cannot be changed. Since BAJAOVRLAY-36 updateItemFields also takes layerId (the command keeps its name): the next take of the item uses the new layer, while an instance already on air from it stays where it is; the graphic still cannot change, and a graphicId sent is dropped by the command schema. deleteItem (itemId) removes the item and renumbers the rest. reorderItems (rundownId, orderedItemIds) takes the full list and is refused with ITEMS_NOT_A_PERMUTATION unless it holds exactly the rundown's items, once each. moveCursor (rundownId, itemId or null) is refused for an item of another rundown. takeItem (itemId) resolves the item's fields into data and runs the server's one internal take step (putGraphicOnOutput, which every take and preview ends in), always on the program output, and the new instance carries the item's itemId; an instance keeps its itemId even after the item is deleted. takeNext (rundownId) is a takeItem of the item at the cursor and is refused with RUNDOWN_CURSOR_EMPTY when the cursor is on nothing.

The cursor rules: the first item created in an empty rundown gets the cursor and no later create moves it; a take moves the cursor only when the item taken was the cursor item, to the item after it, or to nothing after the last item (it never wraps to the top), so takeNext always moves it on, while a takeItem of any other item (a row fired ad hoc) leaves the cursor exactly where it was, a cursor on nothing included; deleting the item at the cursor moves the cursor to the item that followed it, or to nothing; reordering keeps the cursor on the same item; a refused command never moves it.

When an item taken with takeItem or takeNext has autoOutAfterMs, the server sends a clearLayer for the item's layer after that delay, as the actor sistema:auto-out, unless the instance has left the layer first. Since BAJAOVRLAY-36 that clearLayer carries target program (the one optional field of clearLayer; without it a clear takes both outputs), so a preview prepared on that layer stays. An actor whose name starts with sistema: is the server itself (no connection is ever given that role) and may send only clearLayer, apart from the macro runner and watchdog (M1, below), the data-source poller and recorder (M2, below) and the refresher of bound fields, sistema:vinculos, which may send refreshBoundInstanceData and nothing else (BAJAOVRLAY-20, below), and the media store, sistema:midia, which may send recordUploadedMedia and nothing else, and is the only actor that may send it (BAJAOVRLAY-19); the authorize step refuses every other command from it with NOT_ALLOWED. The wait lives in memory only: after a server restart nothing is rescheduled and the item stays on air until it is cleared.

Transforms are a registry of named, pure functions (topN(6), formatLapTime, abbreviateUniversity), never free-form expressions. Readable, testable, no surprises on air.

As built by BAJAOVRLAY-40, the registry is packages/shared/src/transforms. transformRegistry.ts lists every entry: an id, a pt-BR label and description, an optional Zod parametersSchema, and apply(value, parameters), which answers { ok: true, value } or { ok: false, reason } with a pt-BR reason quoting the value, never throws, reads no clock and keeps no memory. findTransform(id) reads one entry, and checkTransformParameters(transformId, parameters) is what a config schema runs, so an unknown id or bad parameters are refused when the config is saved, never at poll time. Two families share the one registry:

- Mapping transforms bring outside data into the canonical shapes; a flex source's mapping (§8) uses them, and they are the only ones built. textToNumber ("12,5" and "12.5" both read 12.5; "1.234,5" is refused, not guessed), textToInteger, secondsToMs (278.293 to 278 293), lapTimeTextToMs ("4:38.293", "4:38,293", "278.293", "1:02:03.4"), isoDateTextToMs (a moment with no zone is refused, since a guessed zone puts a clock three hours off), unixSecondsToMs, trimText, and mapValues, the one with parameters: a table from the source's value (a number or boolean looked up by its JSON text, "4", "true") to any JSON value, so status codes, flag codes and run switches become canonical values; a value missing from the table is refused, never passed through.
- Binding transforms shape canonical data for a graphic. As built by BAJAOVRLAY-20: topN (parameter n, 1 to 60: the first n entries of the positions or standings list), formatLapTimeAsText (ms to "4:38,2", tenths cut, never rounded, "0:59,9" under a minute, "1:02:03,4" past an hour), formatGapAsText (parameter unit, ms or laps: "+12,3 s", past a minute too, or "+1 volta" / "+2 voltas") and shortenSchoolName (parameter maxLength, 4 to 60: cut at the last whole word that fits, "…" counted, never an abbreviation guessed; the abbreviateUniversity of the original design). Each declares the value types it reads and the one it gives (topN gives back the list it read).

Every entry is marked with its family (mapping or binding). checkTransformParameters takes the family of what is saved, so a flex mapping refuses a binding transform (reported at its transformId) and a binding refuses a mapping transform; the flex form offers mapping transforms only (listTransformsOfFamily) and the item editor binding transforms only.

dataSources, as built in M2 (BAJAOVRLAY-17), is three slices. dataSources (saved): id, label, kind (simulator, replay or, since BAJAOVRLAY-40, httpJson; the Baja app is a configuration of httpJson, not a kind of its own), config (the kind's own Zod schema in packages/shared/src/dataSources, which the page's forms and the server's adapters share), pollIntervalMs (500 to 60 000), isEnabled, isRecording, pollNowRequestedAtMs (optional), and status: lastAttemptAtMs and lastOkAtMs (optional), lastError (pt-BR text or null), consecutiveFailures, isStale, staleAfterMs (three poll intervals), recordingError (pt-BR text or null) and failingSinceMs (optional: the moment of the first failed poll since the last good one or since it was turned on, kept by later failures, removed by a good poll and by turning the source on or off, kept across a restart; gate 2 re-check of PR #16, João). A source is stale ("atrasada") when its last poll failed, or when no good poll came within staleAfterMs; a source that is off is never stale, it is off. The control page's chips add one rule on top (gate 2 of PR #16, João): a stale source with an error reads red "Erro" once 60 s or more have passed since failingSinceMs on the server's clock (not since lastOkAtMs, which stands still while a source repeats the same data), or at once if it never had a good poll; under a minute, or stale with no error yet (after a restart, or just turned on again), it reads amber "Atrasada", its "há N" counted from failingSinceMs, or from lastOkAtMs when it is late without failing; the header chip counts by the same rule ("Fontes: 1 ok · 1 atrasada · 1 com erro"), and the last data stays on screen in every case. One source, "Simulador — Enduro" (id simulador-enduro, kind simulator, default config, every 2 s), is seeded off on the first boot and on a database with none. dataSnapshots (saved): per source, sourceId, receivedAtMs and shapes, the canonical shapes (§8) of its last good poll; a failure keeps it and marks the source stale, never blanks it (rule 4), and after a restart every source that was on comes back stale, with its snapshot when it has one, until its next good poll (unlike turning a source on, which marks it stale only when it has a snapshot). recordings (memory only, rebuilt at every boot from DATA_DIR/recordings/<sourceId>/*.jsonl): id (<sourceId>/<fileName>), sourceId, sourceLabel, fileName (the start moment in ISO 8601 with ':' made '-', .jsonl; a second recording of the same source in the same millisecond adds -2, -3, ... after the moment), startedAtMs, endedAtMs (null while recording) and snapshotCount (the lines in its file: counted only once each line is written, from the recorder's recordRecordingProgress; at boot, the snapshotNumber of the file's last whole line, the boot reading only the two ends of each file). The bookkeeping is pure state, changed by the reducers; the recorder writes the lines and reports them. A restart closes every recording (no source comes back recording). At boot a stored snapshot that fails today's schema is dropped with a warning (its source stays); a stored source that fails its schema stops the boot.

The httpJson kind, as built by BAJAOVRLAY-40 (HttpJsonConfigSchema in packages/shared/src/dataSources/httpJsonConfig.ts). Its config is requests and mappings. requests holds 1 to 5 requests, each a requestId unique within the source ("classificacao"), an http or https url with no user or password in it, and headers and queryParameters, each a list of { name, value } or { name, valueFromEnvironment }. A request is GET only and has no method key at all, because a poll must never change anything on the other side. mappings is the flex mapping (§8). The schema checks that every requestId a mapping names exists and that every transformId exists in the registry with valid parameters, so createDataSource and updateDataSource refuse a bad config with INVALID_DATA_SOURCE_CONFIG naming config.<path>, in pt-BR.

Secrets never enter state. The dataSources slice is sent to every operator connection and written into the event log, so a token typed into a config would sit in the database, the log and every browser. A secret header or query parameter therefore names an environment variable (valueFromEnvironment), which the server reads at every poll. Only names starting with BAJAOVRLAY_SOURCE_ are accepted, checked by the schema, so a config cannot name any other server variable; .env.example documents the prefix with an example. The prefix alone does not keep a BAJAOVRLAY_SOURCE_ secret on the server, since a config could name one and point at any address: BAJAOVRLAY_SOURCE_ALLOWED_HOSTS does (gate 2 on PR #17). It is a comma-separated list of hosts ("cronometragem.local", any port) or host:port ("cronometragem.local:8080", that port only), compared without regard to capitals, an IPv6 host in brackets, read once at boot (a bad entry stops the boot) and handed to the store's reducers in their context, to the poller and to the sample route. With the list set, a request to a host off it is refused with "O servidor não busca dados em <host> (<request>): esse endereço não está em BAJAOVRLAY_SOURCE_ALLOWED_HOSTS.", and createDataSource and updateDataSource refuse such a config with DATA_SOURCE_HOST_NOT_ALLOWED and the same sentence. With the list unset, any host may be fetched but a request naming a variable is refused ("A requisição <request> usa uma variável de ambiente, mas BAJAOVRLAY_SOURCE_ALLOWED_HOSTS não está definida no servidor; …"), and the server logs a boot warning. Both checks run before any variable is read, so a request to a host off the list, or any request while no list is set, cannot tell which variables are set. To a host on the list, "não está definida" still names a missing variable; that is accepted because a listed host receives the value anyway. A variable that is not set fails the poll with "A variável de ambiente BAJAOVRLAY_SOURCE_BAJA_TOKEN não está definida no servidor.", and no log line or error quotes a header value or the query.

Snapshot storage and messages, as built by BAJAOVRLAY-40. Each source's snapshot is saved as its own row of the data_snapshots table (sourceId as primary key, the whole snapshot as JSON, updatedAt), not in the slices table, so a poll of one source writes only that source's row and deleteDataSource removes only its row, in the same transaction as the command's other rows. The in-memory dataSnapshots slice the reducers see is still one list. At boot, the single dataSnapshots row of the slices table that an older database holds is split into one row per source, once, and removed. On the WebSocket, an operator's hello still carries every snapshot (a screen's carries none); after it, a change to one source's snapshot travels only in the server message dataSnapshot (sourceId, snapshot, or null when the source was removed, and serverNowMs), one per changed source, sent to operator connections just before the slice or slices message of the same change. A slice or slices message never carries dataSnapshots, a no-op poll sends nothing and a failed poll sends no dataSnapshot, and the control store merges the message by sourceId (null removes that source's entry). So a 60-car poll of one source no longer rewrites and re-sends every other source's snapshot.

The data-source commands. createDataSource (label, kind, config, pollIntervalMs) makes a source, off, with an id the server makes; the config is checked by the kind's schema and refused with INVALID_DATA_SOURCE_CONFIG naming config.<path>, and the page may never set a timeline start (the server drops it). updateDataSource (sourceId, and any of label, config, pollIntervalMs) carries the stored timeline start over, so an edit does not restart a race; a simulator whose speed changed keeps its simulated moment, and a replay whose recording, offset or speed changed starts again from the top. deleteDataSource removes the source and its snapshot; its recordings stay. setDataSourceEnabled turns a source on (a simulator's race starts only when it never started, a replay starts from the top every time; error, failure count and failingSinceMs are cleared) or off (not stale, failingSinceMs removed, snapshot kept, recording closed). pollDataSourceNow stamps pollNowRequestedAtMs, which the poller sees and polls at once unless a poll is in flight. restartSimulatedRace (sourceId; "Reiniciar corrida", gate 2 of PR #16, João) moves a simulator's config.simulatedStartAtMs to now, so within one poll interval it answers the green flag again (a poll already in flight read the old start and stores the old race once more); it is refused for a replay with DATA_SOURCE_NOT_A_SIMULATOR and for a simulator that is off with DATA_SOURCE_DISABLED. startRecording and stopRecording ("Gravar", "Parar gravação"; a recording opens at 0 snapshots); starting an already recording source and stopping one that is not are answered ok and change nothing; pollDataSourceNow, restartSimulatedRace and startRecording on a source that is off are refused with DATA_SOURCE_DISABLED, a replay naming an unknown or still open recording with RECORDING_NOT_FOUND, a flex config with a request to a host off a BAJAOVRLAY_SOURCE_ALLOWED_HOSTS that is set (createDataSource, or updateDataSource carrying a config) with DATA_SOURCE_HOST_NOT_ALLOWED, an unknown source with DATA_SOURCE_NOT_FOUND. recordDataSourcePoll (sourceId, result: ok true with shapes and receivedAtMs, or ok false with error and attemptedAtMs) is sent only by the poller: every shape is checked against its canonical schema in the reducer, and a bad, unknown or missing shape makes the whole poll a failure whose error names the path in pt-BR (a poll never half-succeeds); a good poll stores the snapshot and makes the source healthy (the recording's count waits for the recorder, below); a failed one marks it stale and counts the failure, keeping the snapshot and lastOkAtMs, and sets failingSinceMs when it is not set yet (a good poll removes it); a poll for a source deleted or turned off a moment ago is answered ok and changes nothing. A good poll that repeats the stored shapes on a healthy source is a no-op: nothing is saved, logged or broadcast, and its timestamps are not written (the poller judges lateness from its own memory of the last good poll).

The actors: the poller of each source signs as sistema:fonte:<sourceId> and may send only recordDataSourcePoll for that same source; the recorder signs as sistema:gravador and may send only stopRecording, which it does with a failureMessage when a write to the file failed or the recording reached its cap (6 h, or a next line that would take the file past 300 MB; the source shows it as recordingError and keeps polling), and recordRecordingProgress (recordingId, snapshotCount: the lines now in that recording's file, also for a recording closed a moment ago), left out of the event log like a routine poll; operators and renderers may never send recordDataSourcePoll or recordRecordingProgress, and an operator's stopRecording may not carry a failureMessage (NOT_ALLOWED).

The event-log exception: a poll every two seconds would bury the operator's history (the eventLog slice keeps only the newest 200 rows), so recordDataSourcePoll writes an event-log row only when the source's health changes: isStale flips (the source goes stale or recovers) or the lastError text changes (an invalid payload is logged the first time it appears, not every poll). Every other poll saves its slices with no row, and so does every recordRecordingProgress, which follows each written line. Operator commands, the recorder's stop included, are logged like any other command (an accepted command that changes nothing writes no row, as since 2026-10-10), and a logged poll row carries a trimmed payload: the type, the sourceId and a result of ok with receivedAtMs and the shape names, or ok false with attemptedAtMs and the error, never the shapes (a poll refused by the authorize step or the reducer is trimmed the same way, and one that fails validation keeps only its type and sourceId).

Screen connections receive only the slices they draw (an allowlist, PR #17 gate 2): the renderer OBS loads (/ws?role=renderer) and the control page's "Programa" and "Prévia" frames (/ws?role=monitor) get layers, graphics, instances and previewClearedLayerIds in their hello and every other slice as an empty list, no later message carries any other slice (and they are never sent a dataSnapshot message), and a change of no drawn slice sends them nothing (apps/server/src/core/ws/slicesSentToScreens.ts), because graphics get resolved data only, a 60-car snapshot every two seconds is a frame-drop risk in OBS, and a slice a screen never receives (a data source of a kind an older page does not know) can never make it refuse its hello. GET /api/v1/state applies the same filter when called with ?role=renderer or ?role=monitor (another role is answered 400 INVALID_STATE_ROLE), and each renderer page calls it with its own role when its hello is late; with no role it returns every slice. The roles are not proven, so the allowlist keeps race data out of the screens and saves them work, but keeps nothing secret from a client that leaves the role off. GET /api/v1/data-sources/{sourceId}/snapshot returns one source's snapshot.

Pages reload themselves when the server's build changes (PR #17 gate 2). pnpm build first writes build-id.building.json at the repository root (scripts/writeBuildId.js: the moment the build started, in UTC, as the id), both Vite builds embed that id, and only once every package has built is it copied to build-id.json (scripts/publishBuildId.js). The server reads build-id.json once, at boot, and sends it as buildId in every hello (optional in the schema, so an older server's hello still parses): it names the build this process runs, so a failed or running build never changes it, and a finished one takes effect at the restart, with the new server code. The control page and the renderer each read buildId from the raw hello before their own schema checks the rest (so a page that refuses a newer server's hello still reloads), compare it with their own id and call location.reload() when the two differ, at most once per announced build (gate 2 re-check of PR #17, João): the server build a page last reloaded for is kept in sessionStorage, under a key carrying the page's address (path and query, since the control page and its Programa and Prévia frames share one tab's sessionStorage and one page's reload must not hold back the others), and written before the reload, so a lasting mismatch costs one reload rather than a loop, and a newly announced build reloads once more at once. Only when that id cannot be read or written does the older rule apply, at most once a minute by the moment of the last reload, a reload skipped as too recent being tried again once the minute is over; a page whose storage cannot be used at all does not reload (packages/shared/src/build). The one lasting mismatch known: a page loaded between a finished pnpm build and the restart carries the new id against the old, reloads once for the old id (an OBS source blanks once, not once a minute); the restart announcing the page's own build reloads nothing, and only a restart announcing yet another build reloads it once more, so the restart still follows the build. With no build-id.json (development) the server sends no id, and a page from the Vite dev server has none, so nothing is compared there. A page opened before PR #17 ignores the field and needs one reload by hand after that upgrade.

overrides: sourceId, path, value, reason, setBy, setAt. Operator-typed values that win over the source until cleared. Shown as a badge everywhere the path appears.

As built by BAJAOVRLAY-20 (packages/shared/src/overrides), an override is keyed by its source and either a session field (scope session: eventName, sessionName, sessionKind, state, scheduledDurationMs or lapsCompletedByLeader; never the clock, four values that only mean something together) or one car's field (scope car, carNumber: teamName and schoolName, in the positions and the standings, and status, in the positions), and carries value, reason (required), setBy (the actor) and setAt (the command's moment). A car's correction applies to every entry of that car in that source's positions and standings, whatever its place; place-based corrections are not offered, because they would land on another team after the next pass. Points are not correctable (gate 2 of PR #18): they are the organisers' result, and a wrong one is fixed at the source. Laps, times, gaps and ranks are not correctable: one changed alone would break the order the shape's own rules keep, and the shape rules are not checked again after a correction. The overrides slice is saved (a stored row that fails its schema stops the boot); screens never receive it. setOverride (sourceId, scope, field, carNumber for a car, value, reason) is refused with DATA_SOURCE_NOT_FOUND for an unknown source and INVALID_OVERRIDE_VALUE when the value does not fit the canonical field (the shapes' own field schemas, findProblemInOverrideValue); a correction of the same key replaces the earlier one in its place. clearOverride (the key) removes it, and clearing one that is not there leaves no trace. Both are for operators only. deleteDataSource also removes that source's corrections. Every binding reads its source's data with the corrections laid over it (applyOverridesToSnapshotShapes): at the take, at every refresh, on the item editor's "Valor agora" line and on the "Fontes" tables, and setting or clearing one rewrites every bound instance on air at once (refreshBoundInstanceData, below).

instanceBindings (BAJAOVRLAY-20): one entry per instance on air or in preview that reads a source, its instanceId and boundFields (fieldKey and binding, in the item's field order), written at the take or preview from the item as it was then: on program its live bindings only, on preview its frozen ones too (takePreview reads those again). The refreshes read this slice, never the item, so editing or deleting the item does not change what is on air, as with the rest of the instance. reduceCommand drops the entry of any instance a command removed (a clear, a replace, a promoted or discarded preview), in that one place. Two things change an entry after the take (gate 2 of PR #18): an operator's updateInstanceData drops the live binding of every field it sends (the whole clock if it sends any clock field; the entry goes when nothing is left), so the next refresh does not put the source's value back over what was typed, until the next take reads the item again; and a refresh the graphic refused in part writes the refused keys as refusedFieldKeys (below). It is saved with the instances (the plainer of the brief's two choices); at boot an entry whose instance was dropped (a preview) goes too, and its row is written again. Screens never receive it: graphics get resolved data only (architecture rule 3). Since BAJAOVRLAY-19 an entry also holds entityFields (fieldKey and entityReference), the fields of the instance that read the entity library, on program and preview alike (a reference is always live), left out when there is none; boundFields may then be empty. Kept on the same entry, a spell of refusals, a value typed on air (which releases that field's reference) and "Tomar" (which carries them to program) work for them unchanged.

instances (what the renderer mirrors): id, layerId, itemId, target (program or preview), resolvedData, currentStep, status (one of loading, ready, on-air, stopping, failed), statusDetail (optional; why a failed instance failed, as the renderer reported it), takenAt, fieldsChangedOnAir (optional; see below). A new instance is loading until a renderer reports it on-air or failed, and an on-air instance becomes failed if a renderer reports a failure afterwards; a failed instance stays in the slice until it is cleared or replaced, never removed on its own.

entities: tables for teams, people, sponsors, scheduleSlots. Teams carry number, name, university, city, logo, car photo. Sponsors carry tier and roll weight.

As built by BAJAOVRLAY-19 (packages/shared/src/entities), the library is four slices, each saved as a row of the slices table, none seeded, and none sent to screens. teams: carNumber (a whole number from 1, the positions' rule, each car once), teamName, schoolName (short, "UFPR"), schoolFullName (optional), city and state (one of the 27 UFs, in capitals; both optional since gate 2 of PR #23, so a team card drops its place line without them), logoMediaId and carPhotoMediaId (optional), and logoOnLightPlate (optional, left out meaning no: whether the team card puts the logo on its small light plate, for a dark logo or one on its own white box; chosen by hand per team, never detected, BAJAOVRLAY-24). people: personId, name, role, carNumber (optional, the person's team) and photoMediaId (optional). sponsors: sponsorId, name, tier (master, ouro, prata, bronze or apoio), logoMediaId (optional: a CSV never carries one), rollWeight (a whole number from 1 to 10) and logoOnLightPlate (optional, left out meaning no: the team's rule, chosen by hand in Cadastros or the CSV's placa_clara column, BAJAOVRLAY-23; a sponsors row stored before it boots unchanged; the tiers are untouched until the sponsor roll, BAJAOVRLAY-26). scheduleSlots: slotId, sessionName, sessionKind (the session shape's list), startsAtMs, endsAtMs (optional, after the start) and place (optional); findStatusOfScheduleSlot works out "a seguir" before the start, "em andamento" from the start until the end, "concluída" from the end on, a slot with no end running until the next slot starts (the last stays in progress), and the status is never stored. Ids of people, sponsors and slots are made by the page (makeRecordId, a version-4 UUID from crypto.getRandomValues, which plain http on the LAN offers, unlike crypto.randomUUID) or carried by a CSV. A record no longer in the library is named in words, never by its id ("uma pessoa excluída dos cadastros"). Every refusal of a record is a pt-BR sentence naming its field (ptBREntities.ts), which the server, the Cadastros form and the CSV preview share. A stored row that fails its schema stops the boot.

The entity commands, operators only. upsertEntity (entityType and the record, checked by that kind's schema) adds the record or replaces the one of the same key in its place; one saved exactly as stored changes nothing. deleteEntity (entityType and the key) removes it, also while items reference it (they then refuse their take, naming the record; what is on air keeps its last value), and deleting what is not there is answered ok. importEntities (entityType and 1 to 1000 records, each key once) upserts all of them in one change, one event-log row whose payload keeps the type, the count and the keys, never the records; an import its schema refuses is logged with its type, the entityType as sent and the record count only, and the CSV preview refuses a file of more than 1000 lines before sending. An upsert or an import naming an image the media store does not hold is refused with MEDIA_NOT_FOUND, naming the field.

media (BAJAOVRLAY-19, packages/shared/src/media): one record per image the store holds under DATA_DIR/media/<mediaId>: mediaId (the SHA-256 of the bytes, 64 lower-case hexadecimal digits, so the same file is one media, and the path-safety check), fileName (as uploaded, shown, never a path), contentType (image/png, image/jpeg, image/webp or image/svg+xml), sizeBytes (at most 5 MB), widthPx and heightPx (read from the header) and uploadedAt. Saved; screens never receive it. POST /api/v1/media (multipart, the field "file") checks the bytes, never the name (a program renamed logo.png is refused with 415, a file over 5 MB with 413, also streamed in chunks with no length, an image whose size cannot be read with 422, no file with 400). Until M4 brings logins (gate 2 of PR #23) it also refuses with 507 a new image when the store holds 1000 images or would pass 500 MB, or when the disk (statfs) would keep less than 1 GB free, and with 403 an upload whose Origin is not the server's own address (no Origin, as curl or Companion send, passes). It then writes the file, and records it with recordUploadedMedia as the actor sistema:midia, which may send nothing else and is the only one that may send it; the reducer stamps uploadedAt with the command's moment, and an id already listed changes nothing. GET /media/<mediaId> serves only an id the slice lists, with a year of cache (an id never changes content), nosniff and the CSP of §3.3. deleteMedia (mediaId, operators) is refused with MEDIA_IN_USE while a team, person or sponsor names the image, an item field holds its /media/<mediaId> as a typed value, or any instance on air or in preview shows it at any depth of its data (findUsesOfMedia, shared with "Limpar imagens sem uso"), listing each use; the media service then removes the file at once, so the folder's size, shown on Cadastros, is the slice's sum.

theme: semantic tokens for the on-air graphics (brand primary color, display font, logos, event name and year). One active theme. As built in M2 (BAJAOVRLAY-22): not a slice yet. Ardósia is the only theme and the renderer loads it statically from /theme/ (§3.3); choosing a theme by command is left for later.

macros: id, label, commands (a list of Command).

As built in M1 (BAJAOVRLAY-16): an item has a home instead of a rundownId, either a rundown (kind rundown, rundownId) or a quick-fire panel (kind quickFire, panelId), and its order counts within that home; items stored with rundownId are converted at boot and written back once, and a stored item with no home stops the boot. The slice quickFirePanels holds id, name, order; the panel "Atalhos" (id atalhos) is seeded, a panel with items or the last panel cannot be deleted, and createQuickFirePanel, renameQuickFirePanel, deleteQuickFirePanel and moveItemToHome (itemId, home, order; also how buttons are reordered) change them. A panel item is ad hoc by definition: it never gets or moves a rundown cursor, and moveCursor refuses it. A macro is id, label, color and steps, each step one of takeItem (itemId), clearLayer (layerId), clearAll, or wait (ms, 1 to 10 000), saved with createMacro, updateMacro and deleteMacro. runMacro (macroId) records a run in the macroRuns slice (macroId, startedAt, currentStep, isStopRequested), which lives in memory only and is empty at boot; a server-side runner then sends each step through the normal command path as the actor sistema:macro:<macroId>, strictly in order, a wait delaying the next step, and advances or ends the run with its own two commands. A refused step stops the macro, and nothing earlier is undone: on-air state is never rolled back automatically. An endMacroRun the store fails to apply is sent again a second later until it goes through, so a fault never leaves every macro locked. While any macro runs, runMacro, and updateMacro or deleteMacro of the running one, are refused. An operator stops a run with stopMacro (macroId; "Parar"), which only sets isStopRequested on the run: the runner sends no step after the one in progress, a wait in progress is cut short because it puts nothing on air, and the run is ended with endMacroRun as usual; nothing is rolled back. stopMacro of an unknown macro is refused with MACRO_NOT_FOUND, and for a macro that is not running, or a run already marked, it is answered ok and leaves no trace. A watchdog started with the runner gives each run a limit of the sum of its waits plus 30 s and ends any run still listed at that moment with endMacroRun as the actor sistema:macro-watchdog, with a warning log line naming the macro and the limit; a run that leaves the slice calls its watchdog off, and the runner forgets a run ended by the watchdog. The macro actor may send takeItem, clearLayer, clearAll and its own bookkeeping; sistema:macro-watchdog only endMacroRun, of any macro; sistema:auto-out still only clearLayer; operators may send stopMacro but never advanceMacroRun or endMacroRun.

eventLog: append-only: ts, actor, command, payload, result.

As built by BAJAOVRLAY-44, the event inbox (packages/shared/src/eventInbox, apps/server/src/modules/events). The canonical shapes gain incidents (§8) and the positions entries bestLapNumber. Two saved slices, which screens never receive. events: the newest 200 events, oldest first, each the detected event (eventId, kind newIncident, fastestLap, leaderChanged, manual or superChat, sourceId or null for a typed one, detectedAtMs, and payload: carNumber and, when known, teamName, schoolName, noticeKind penalty, warning, incident or notice, reason, penaltyText, lapNumber, lapTimeMs and lapTimeText) plus status (pending, queued, onAir, shown, dismissed, expired), statusChanges (each status with its moment) and, while on air, instanceId; the event_log table keeps every event, since each detection, show, dismissal and expiry writes a row carrying it. eventRules: one rule per kind (mode ask, auto or ignore; itemId or null; durationMs; maxAgeMs or null), seeded with João's defaults (incidents ask 10 s with "Penalidade"; fastest laps auto 8 s with "Volta mais rápida", expiring after 2 minutes; leader changes ignored until a notice is designed for them (6 s, 2 minutes once set to auto); manual events ask 10 s with "Penalidade"; Super Chats ask 15 s with no item) once per database, together with the quick-fire panel "Avisos" holding those two items; a Super Chat on auto and a manual event on ignore are refused by the schemas, and an auto rule with no item records its events as pending (gate 2 of PR #22). ### Commands, the only way state changes

takeItem, clearLayer, clearAll, nextOnLayer, previewItem, stopPreview, takePreview, updateItemFields, saveOnAirChangesIntoItem, reorderItems, moveCursor, runMacro, stopMacro, setOverride, clearOverride, setDataSourceEnabled, upsertEntity, importEntities. Since BAJAOVRLAY-20, setOverride and clearOverride are built (overrides, above), and the server's refresher sends refreshBoundInstanceData (below). Each has a Zod input schema; each is validated, authorized, applied, logged and broadcast, in that order, in one code path. Since BAJAOVRLAY-17 the data-source commands are createDataSource, updateDataSource, deleteDataSource, setDataSourceEnabled, pollDataSourceNow, restartSimulatedRace, startRecording, stopRecording, the poller's recordDataSourcePoll and the recorder's recordRecordingProgress (dataSources above), and a routine poll and a recording's progress are the commands that skip the "logged" step. Since BAJAOVRLAY-19 the entity library's are upsertEntity, deleteEntity and importEntities, and the media store's deleteMedia and the server's recordUploadedMedia (entities and media above); importEntities stands where the original list had it.

updateInstanceData (instanceId, data) changes an instance that is on air, or in preview, without replacing it: the fields in data are laid over resolvedData (top-level keys only), the result is validated against the JSON Schema in the graphic's manifest, and the instance keeps its id, so the renderer calls updateAction instead of taking the graphic off and on again. An unknown instance is refused with INSTANCE_NOT_FOUND; data the schema does not accept, in a take or in an update, is refused with INVALID_GRAPHIC_DATA and a pt-BR message naming the field.

As built in M1 (BAJAOVRLAY-14), the take step (the public command takeGraphic until BAJAOVRLAY-37, now the server's internal putGraphicOnOutput, handed graphicId, layerId, data, target, takeTimeFieldKeys and itemId) and updateInstanceData (instanceId, data, and optionally takeTimeFieldKeys) prepare the data in steps before that check, in this order. First the nulls: a top-level null means "no value", so a take leaves that key out of the data and updateInstanceData takes that key off the instance's resolvedData, which is how an optional field leaves the air; a null deeper than the top level is a value like any other. Then the stamps: takeTimeFieldKeys (a list of field names, empty when left out) names the fields the server fills with the command's own moment in wall-clock milliseconds, the same moment as takenAt and the event-log ts, replacing whatever the command sent for them, so a client never sends its own clock. Only a field the graphic's schema declares as an integer with v_baja.role wallClock may be named: any other key is refused with INVALID_GRAPHIC_DATA before anything is stamped, and a graphic without a schema accepts no stamp. Then, in updateInstanceData only, the update rule the manifest names in v_baja.updateRule, if any. Update rules are a registry of named pure functions (apps/server/src/core/store/updateRules/), like the transforms above and never free-form expressions: a rule is handed the data on air, the fields sent, the keys stamped, the keys cleared and the command's moment, and hands back the fields to write. The one rule so far, carryClockForward, keeps a race clock from jumping: when the time, the running switch or the mode changed and the reference moment was neither stamped nor sent with a new value, it writes the typed time, or else the time on screen at that moment (never below 0), together with that moment as the new reference; when the mode changed and no time was typed, the time written is the whole second the screen was showing (elapsed rounds down, remaining up), so the number on screen does not move at the press; the sum and the rounding are the graphic's own, kept once in packages/shared/src/clock. A manifest that names an unknown rule, or one whose fields its schema does not declare, is warned about at boot and every update of that graphic is refused with INVALID_GRAPHIC_DATA; it can still be taken. Then the no-change check: an updateInstanceData whose result equals the data already on air (no field sent, nulls only for keys that are not on air, or the values already on air sent again) changes nothing and leaves no trace: it is answered ok, and nothing is saved, logged or broadcast; a stamp writes the moment of the command and is therefore a change. Last the manifest's schema, on the whole result: a required field taken off is refused with INVALID_GRAPHIC_DATA. takeItem goes through the steps of a take with the keys of its takeTime fields as the stamp list, so an item whose takeTime field is not a wall-clock field of the graphic is refused at the take, and an item field stored as a literal null goes on air without that field. createItem and updateItemFields run the same check on the takeTime fields they carry and refuse such a field with the same message, so it is not stored either. The steps from the nulls to the schema are one function, prepareInstanceDataUpdate (core/store/instanceDataUpdate.ts), shared with refreshBoundInstanceData.

refreshBoundInstanceData (instanceId, data), as built by BAJAOVRLAY-20, writes a source's new values for an instance's live bound fields; since BAJAOVRLAY-19 also the library's new values for its entity fields, after a team, person, sponsor or slot changed. Only the server's refresher sends it, as the actor sistema:vinculos, which may send nothing else; no operator, screen or other server job may send it (to change the source's value an operator sets a correction, setOverride; a value typed over a live field on air releases that field's binding, see instanceBindings). It goes through updateInstanceData's steps (nulls, the update rule, the no-change check, the manifest schema), so the instance keeps its id and the renderer updates it in place; a whole clock reading sent by the clock group carries its own moment, so carryClockForward passes it through as it came. It never adds to fieldsChangedOnAir (those are the operator's changes) and never touches a preview's origin or the fields it stamps at the take. A refresh for an instance that has just left is answered ok and changes nothing, like a late poll. A refresh the graphic's schema refuses as a whole does not freeze the instance (gate 2 of PR #18): the clock group (its four fields together) and each other field are tried alone, each on the data the parts before it left; what fits goes on air, what does not stays as it was, and the refused keys are written on the instance's entry of instanceBindings as refusedFieldKeys, which Camadas shows as "atualização recusada" (the fields in its tooltip). A refresh that fits as a whole clears them. The event-log exception: an applied refresh writes no row (isLeftOutOfTheEventLog), for the reason a routine poll does not; the refresh that begins a spell of refusals (no refusedFieldKeys before, some now) is applied as far as it fits and its row is written as failed with the whole set's reason (the reducer's refusalWrittenToTheEventLog), and the rest of the spell writes none. The spell lives in the slice, so it survives a restart; the refresher keeps no memory of its own and applyCommand takes no options. An instance with no entry has nowhere to keep a spell, so its refresh is refused as a whole, as any update.

As built by BAJAOVRLAY-37, everything on air or in preview comes from an item. The public commands takeGraphic and previewGraphic are removed: their schemas are gone, so a client sending one is refused with INVALID_COMMAND naming type. Every instance the server makes carries the itemId of the item it came from; an instance stored without one (put on air by hand before BAJAOVRLAY-37) still loads at boot and can be updated and cleared, and Camadas names it "sem item". takePreview refuses a preview with no itemId with INSTANCE_WITHOUT_ITEM, a guard no command can reach since previews are dropped at boot. updateInstanceData works on preview instances as on program ("Atualizar prévia"), keeping the id and the itemId, so takePreview promotes exactly what was seen: a key it sends with a value and does not ask to stamp leaves the preview's takeTimeFieldKeys (a typed moment survives the take), and an edited automatic preview becomes manual. On an instance with an itemId it writes fieldsChangedOnAir: the instance's earlier list, plus each top-level key the operator sent (in data, a null included, or in takeTimeFieldKeys) whose value now differs from what the item stores now (a literal compared by content, a field missing on air equal to a literal null or to no field; a takeTime field differs whenever it was sent). A key the update rule wrote by itself is not listed, and no update takes a key off the list; updateItemFields takes off the lists of the item's live instances (program and preview) every field whose stored value it changed, a new take carries no list, takePreview carries the preview's list to program, and left out means nothing changed. saveOnAirChangesIntoItem (instanceId, wallClockFields: keepMoment or atTake, required) writes each listed field into the item as a literal of its value on air (a field missing on air as a literal null), except a field the graphic's schema marks v_baja.role wallClock with atTake, which is stored as takeTime, and takes the saved fields off the lists of the item's live instances; a clock is saved whole: when any listed field has a clock role (clockTime, wallClock, clockRunning, clockMode), all of the graphic's clock fields are saved, so a clock stopped on air (only the running switch listed) comes back at the time it was stopped at; it is refused with INSTANCE_NOT_FOUND, INSTANCE_WITHOUT_ITEM, ITEM_NOT_FOUND (the item was deleted) or NOTHING_CHANGED_ON_AIR, and only operators may send it. The answer to an accepted createItem names the new item: CommandOutcome and the WebSocket commandResult carry createdItemId.

As built in M1 (BAJAOVRLAY-36), the slices one state change changed reach a client as ONE WebSocket message: slice (name, slice) when one slice changed, which is only a refused command since that changes the event log alone, and slices (slices: the changed slices by name, each checked by its own schema; serverNowMs required) when several did, which is every accepted command, as it changes its own slices and eventLog. The renderer turns either into one delivery and the control page into one store update, so no client ever draws some slices of a change new and the others old (sent one per slice, "Prévia: limpar" on a previewed layer showed the program clock on the Prévia page for a moment).

As built in M1 (BAJAOVRLAY-14 follow-up), every hello, slice, slices and dataSnapshot message carries serverNowMs, the server's wall clock as the message is built. A renderer page and the control page each keep the difference between that and their own clock as the median of the last five samples, and readServerAlignedTimeMs (packages/shared/src/clock) hands back their own clock plus that difference; the race clock reads it instead of Date.now(), so a clock on air counts from the server's clock even when the OBS machine's clock is off. The difference is kept in one property of globalThis, because the renderer and each graphic are separate bundles. In "Edição rápida", for a graphic whose manifest names carryClockForward and marks its four clock fields with the roles clockTime, wallClock, clockRunning and clockMode, the untouched time field shows the time on screen, live; the form still holds the reference that is on air, so that shown time is never sent.

reportInstanceStatus (instanceId, status on-air or failed, detail optional) is how a renderer says what really happened on screen: it moves a loading instance to on-air or to failed, and an on-air instance to failed when a renderer reports a failure later. Any other report (a second on-air, anything about an instance that is already failed, or a late report about an instance that is no longer there, which is the normal end of a quick clear) changes nothing and is answered ok, not refused. It is the only command a renderer may send, and an operator may not send it (nor the macro runner's bookkeeping or recordDataSourcePoll, above); the authorize step refuses the rest with NOT_ALLOWED. The server's own actors, sistema:, may not send it, and send nothing but clearLayer apart from the macro runner, the macro watchdog, the data-source pollers and the recorder (each limited to its own commands, above). Until login exists a WebSocket connection is a renderer when it connects to /ws?role=renderer (its actor is renderer: followed by the connection id), a monitor when it connects to /ws?role=monitor (monitor: followed by the connection id) and an operator otherwise (operador: followed by the connection id); the role is taken at its word until the LAN PINs of M4. A monitor may send no command at all. Only the program output reports: the page OBS loads (/render/) connects as a renderer, while the program monitor on the control page frames /render/?monitor=1, which connects as a monitor and never sends instanceStatus. With no program renderer connected an instance therefore stays loading.

The renderer does not wrap that command in a command message. It sends the client message instanceStatus (type, instanceId, status, detail optional) after playAction resolves, or after an import, load or play that failed, and the server builds reportInstanceStatus from it and runs it through the same code path as every other command.

## 5. Binding resolution and live updates

1. On take, the resolver walks the item's fields: literals pass through; bindings read the source snapshot at the path, apply overrides, apply the transform; entity references read the entity table. Result: resolvedData matching the graphic's schema. A validation failure refuses the take with a readable message; never a half-rendered graphic.
2. While an instance is on air, every time a data source snapshot changes the resolver recomputes resolvedData for instances with live bindings and, if anything differs, the renderer calls updateAction with only the changed keys.
3. Snapshot bindings are resolved once at take and never touched again.
4. A stale source does not stop live updates from being attempted; it shows a stale badge on the instance in the control page. Operators decide whether to clear.

As built by BAJAOVRLAY-20:

1. At the take and at a preview, resolveItemFieldsIntoGraphicData (core/store/resolveItemFields.ts) is handed everything as plain data: the item's fields, its graphic (which fields are required, their titles, the clock fields by role), the moment of the command, and the sources with their last good snapshots and the overrides. It reads nothing itself. A bound field is read by the shared resolveBindingAgainstSources (packages/shared/src/bindings): the source's last good snapshot, a stale one too, with the source's overrides laid over it, at the path, then the transform. A source that does not exist, a source with no data yet ("Título: a fonte Simulador — Enduro ainda não tem dados."), a shape the source does not send, or a value absent on a required field refuses the whole take or preview with BINDING_NOT_RESOLVED, the field's title first; a value absent on an optional field leaves the field out, as a cleared literal does. The whole clock (path clock) fills the four clock fields by role, after every other field. The same function, against the page's own slices, is the item editor's "Valor agora" line and the rundown's "fonte · não entra agora" hint.
2. Live updates: the refresher (modules/bindings/liveRefresher.ts) watches the store. When snapshots change (a good poll, a deleted source) it refreshes, from a 0 ms timer, every instance with live bindings on a source that changed; when the overrides change, every instance with live bindings. For each it reads the instance's entry of instanceBindings, never the item, and asks buildRefreshOfLiveBoundFields what to send: every live value as one set whenever any differs from what is on air (so the whole clock always moves as one reading), as refreshBoundInstanceData through the one command path (§4). A field that cannot be read now keeps its last good value on air (rule 4: a deleted source, a source with no data, a required value gone); only an optional field whose value the source no longer has leaves the air. The renderer calls updateAction with the instance's new data, as for any update.
3. Snapshot bindings (isLive false) are read once at the take and never refreshed; a snapshot binding in a preview is read again at "Tomar", the same exception as takeTime fields (frozen at the take, not at the preview), refusing the take like any take when it cannot be read. Live fields go to program as previewed; the refreshes keep them current.
4. A stale source does not block a take and does not stop the refreshes. Camadas shows, on the row of an instance whose live bindings read a source that is late or failing, the chip "fonte atrasada" (amber) or "fonte com erro" (red), by the "Fontes" page's health rule (PR #16), and "fonte excluída" once the source was deleted (its refreshes stop and its data stays on air); and "fonte desligada" once it was switched off (its refreshes stop and its data stays on air); a row whose bound value a correction changed carries "valor corrigido", and one whose last refresh the graphic refused in part "atualização recusada". At "Tomar", every key the preview's frozen fields fill is first taken out of the previewed data, so an optional value the source no longer sends goes off air as at any take (gate 2 of PR #18). Operators decide whether to clear.

As built by BAJAOVRLAY-44, detection: the event detection (modules/events/eventDetection.ts) watches every accepted poll and compares the source's new snapshot with the one before it, remembered in memory, with pure detectors (modules/events/detectors): an incident id not listed before, a session best lap that improved (or the first best lap of the session), another car in 1st place. A shape the previous snapshot lacked, or a new sessionId (the simulator's names its race start, so "Reiniciar corrida" or a speed change is a new session), is a baseline; so is a source's first snapshot ever, and the first after it is turned on or its config changes. After a boot the detection starts from the snapshots saved before the stop (gate 2 of PR #22, João), so what happened while the server was down arrives, and an id the inbox already holds is never listed again. Each event found is recorded through the one command path as sistema:eventos, from a 0 ms timer, one recordDetectedEvents each.

As built by BAJAOVRLAY-19, entity references:

1. At the take and at a preview, the resolver is also handed the entity library (teams, people, sponsors, scheduleSlots) and reads an entity field with the shared resolveEntityReferenceAgainstLibrary (resolveEntityFields.ts): the record of the reference's key, then the attribute, an image as /media/<mediaId>. A record not in the library refuses the whole take with ENTITY_NOT_RESOLVED, the field's title first ("Título: a equipe do carro 7 não está nos cadastros."); an absent attribute refuses a required field and leaves an optional one out (no logo: the graphic's no-logo state). A binding to positions.entryOfCar.<field> and a reference to the team of the same carNumber meet in one item with no join: the team card's case.
2. The refresher also watches the four entity slices; when one changes it reads every instance's entityFields and sends what changed through refreshBoundInstanceData as sistema:vinculos, with the same rules and the same event-log exception as a source's refresh: a record gone keeps the last value on air (rule 4), an optional attribute gone is sent as null. A poll does not read them. "Edição rápida" draws such a field read-only (gate 2 of PR #23): "Cadastro › Equipe 42 › Número do carro", the value on air, and "Editar no cadastro", which opens #/cadastros/<kind>/<key> in a new browser tab, Cadastros starting on that record's form; the server still releases a library field typed on air, for an older page.
3. Logos in a list (one per tower row) are not offered: that needs a list join, which a later item adds as a named binding transform (withTeamLogos), never as a free-form expression.
4. Rundown rows and shortcut buttons of an item that reads the library carry "cadastro", or "cadastro · não entra agora" with the take's reason; "Salvar no item" skips a field the item reads from the library, as it skips a bound one.

## 6. Renderer contract

- URLs: /render/program (all layers, 1920x1080, transparent background) and /render/preview with an instanceId parameter (one instance, embedded in the control page).
- Load a graphic: create the custom element inside its layer container, await load with data, then playAction to step 0.
- Replace on the same layer, per the layer's replacePolicy. Default out-then-in: stopAction on the old, dispose, then load and play the new.
- Clear: stopAction (animated), then dispose.
- Next: playAction with delta 1; when the graphic reports it reached its end, the server marks the instance stopped.
- Reconnect: request the full instances slice, dispose everything local, rebuild each on-air instance with skipAnimation true.
- Timing metadata from the manifest (actionDurations) is used by the control page to show "animating" and to sequence macros; the renderer only awaits the promises.
- Later, optional: expose the OGraf Server API over REST so third-party controllers can drive our renderer.

As built in M1 (BAJAOVRLAY-15) the renderer is one page, /render/, and its address says what it is. /render/ is the program output OBS loads: it draws instances whose target is program, connects as a renderer and reports each instance on-air or failed. /render/?monitor=1 draws the same, connects as a monitor (/ws?role=monitor) and reports nothing (the control page's "Programa" monitor). /render/?target=preview draws only instances whose target is preview, connects as a monitor too and never reports, with or without monitor=1 (the control page's "Prévia" monitor frames /render/?target=preview&monitor=1). Only those exact values count, so any other address is the program output. A preview page is the same reconciler and player: the one difference is that a replace there is always the cut (new graphic loaded behind the old one, then swapped with skipAnimation), whatever the layer's replacePolicy; a first preview still animates in and a discarded one out. Preview is whole layers, not one instance: the /render/preview address with an instanceId was not built.

Since BAJAOVRLAY-36 the preview page shows the result, exactly what the screen will look like after the take. One function, selectInstancesForPreviewComposition (apps/renderer/src/previewComposition.ts), picks per layer the preview instance if there is one, else nothing if the layer is in the previewClearedLayerIds slice ("vai limpar"), else the program instance; a previewed layer never shows its program instance. The reconciler composes the previous and the next delivery with it and then diffs as before, so there is no second code path (operationsPerDelivery.ts keeps the previous delivery; a slices message is one delivery, so the instances and the markers of one change are composed together); the program page still draws program instances only and never reads the markers. A program instance the preview page shows gets the same updates as on air; a marker arriving takes the layer's graphic off with its out-animation, and one going away brings the program instance back with its in-animation.

Every ten seconds the server sends each client the message time (serverNowMs), and hello, slice, slices and dataSnapshot messages carry serverNowMs too; a page records each as a sample of the server's clock (§4), and a message without it gives no sample.

## 7. Operator experience, the rules

1. Nothing goes to air without being visible first. Preview is one click and is always the same pixels as program. As built in M1 (BAJAOVRLAY-15): the centre shows two monitors, "Prévia" and "Programa", always side by side and the same size, 480x270 at most and shrinking together (always 16:9) on a narrower window. previewItem (itemId, origin) puts an item on the preview output of its layer, one instance per layer, resolved and checked exactly as a take; stopPreview (layerId, or null for every layer) discards it; takePreview (layerId) sends what was previewed to program without resolving it again, stamping only its take-time fields anew, and moves the cursor as takeItem does. A row of the rundown, a shortcut button's menu and the item editor ("Salvar e prévia") each offer "Prévia", the lines under the Prévia monitor have "Tomar" and "Descartar", and a layer holding a preview is marked "em prévia". With "Prévia automática" on (the default, kept per browser), the item the cursor arrives on is previewed by the page that moved it: after a move by hand with the arrows or a click, and after a take sent from that page that moved the cursor on, so Space, Space is the operator's loop and each item is seen before it airs. Such a preview carries origin auto, and the server first discards every other preview that was itself automatic, on any layer; previews asked for by hand (origin manual: a "Prévia" button, Shift+Space, "Salvar e prévia") stay until taken, discarded or replaced on their own layer. Each preview instance records its origin (previewOrigin). Previews are scaffolding: they survive a reload of the control page and are dropped when the server restarts. Since BAJAOVRLAY-36 Prévia shows the result (§6), and a set is looked at and taken in one go: previewClearLayer (layerId) marks a layer "vai limpar" in the previewClearedLayerIds slice (in memory only, empty at boot) and removes its preview, a preview on a layer removes its mark, and so does any take on program there (takeItem, takeNext, a macro step, a promoted preview: the plan to empty the layer is stale), stopPreview, clearLayer and clearAll remove marks too, and takePreview of a marked layer clears that layer on program. takeAllPreviews promotes every preview (as takePreview, layers in z-order) and applies every mark in one state change, one event-log row and one broadcast, so OBS never shows half a set; it then settles each rundown cursor once: while the cursor item is one of the items it took, the cursor moves to the following item (past the last, it is left on nothing with wasLastItemTakenAtCursor), so the cursor never rests on an item just put on air whatever the layers' order; with nothing previewed or marked, or with any one layer that cannot be taken, it is refused and nothing changes. previewMacro (macroId) discards every preview and mark, then plays the macro's steps onto preview only (takeItem previews the item, clearLayer marks, clearAll marks every layer with something on program, wait is ignored), so Prévia shows the macro's end state and "Tomar tudo" lands it in one cut without the waits; runMacro, which keeps the waits, discards previews and marks first. On the page: "Prévia: limpar" on a Camadas row, "vai limpar" lines, "Tomar tudo" and "Descartar tudo" when two or more lines are listed, and "Prévia" in a macro's ⋯ menu. "Edição rápida" never puts anything new on the preview output; a loaded preview is changed in place with "Atualizar prévia" (rule 3).
2. One-press actions for the common case: take, clear layer, clear all, next. Keyboard: Space = take, Backspace = clear layer, Esc = clear all, Right arrow = next. As built in M1: Space is always "take the item at the cursor" (takeNext), also while the focus is on a button, which is then not pressed; the Right and Left arrows move the rundown's cursor one item forward or back without taking anything, and a click on a row's label puts the cursor on that row. ## 8. Data sources

- Scoring system: REST endpoints on the Baja app (see §18). Poll every 2 to 5 s during sessions; normalized into positions, standings.overall, standings.EVENT, brackets.EVENT, session (state, clock, flags). Since BAJAOVRLAY-40 this is a flex source configuration once its endpoints exist, shipped as a preset by BAJAOVRLAY-18, not an adapter of its own.
- Entities: SQLite tables in the server. CSV import plus UI editing; logos and photos stored under data/media. As built by BAJAOVRLAY-19: four slices of the slices table and the media store under DATA_DIR/media (§4); the CSV of each Cadastros tab has fixed columns (Equipes carro, equipe, escola, escola_completa, cidade, uf, placa_clara, the place columns optional since gate 2 of PR #23, placa_clara "sim" or "não" since BAJAOVRLAY-24; Pessoas id, nome, funcao, carro; Patrocinadores id, nome, cota, peso; Programação id, sessao, prova, inicio, fim, local), is read with ";" or "," and written with ";" and a UTF-8 byte-order mark for Excel in pt-BR, dates as "14/11/2026 10:00" on the computer's clock, and never carries an image (an update from a CSV keeps the record's, and keeps any field whose column the file lacks). The preview marks each line "novo", "atualiza" (the same key) or "erro" with the line and the shared reason, and "Importar" sends the valid lines as one importEntities. "Importar equipes do simulador" loads the simulator's hundred fictional teams (GET /api/v1/entities/simulator-teams, cars 1 to 100 with their schools' cities) for walks and rehearsals, asking first when teams exist. The entity library is not a data source: it is read by entity references, never polled.
- Sheet or JSON URL: a sheet published as JSON, or any other JSON the committee keeps (schedule, speakers), is a flex source (below). CSV is not built.
- Manual: overrides and literal fields. Always available, always visible as such.

Original design (superseded by the as-built paragraphs below): every adapter implements the same interface: a poll function returning a Snapshot, plus a describe function listing the paths it produces (the control page uses this to build the binding picker). Every adapter ships with a recorder (writes snapshots to disk with timestamps), and a shared replayer provides rehearsal mode.

As built in M2 (BAJAOVRLAY-17), the canonical shapes (packages/shared/src/dataShapes). Every source maps into these and graphics bind only to them. Times are integer milliseconds: durations such as lastLapMs, and moments such as updatedAtMs in ms since 1970 on the server's clock. Every entry repeats carNumber, teamName and schoolName (short form, "UFPR"), so a graphic never joins tables. Optional means "the source does not know", never a placeholder such as 0.

- session: sessionId, eventName, sessionName, sessionKind (enduro, acceleration, speed, traction, suspension, maneuverability, other), state (exactly the race clock's flag values: pre, green, yellow, red, checkered, finished; a test reads the manifest so they cannot drift), clock, scheduledDurationMs and lapsCompletedByLeader (optional), updatedAtMs. clock is clockMode (elapsed or remaining), referenceTimeMs, referenceWallClockMs and running: the race clock's own field names, clockMode and not the brief's mode, so session.clock is a ClockReading and a binding feeds the clock with no rename.
- positions: sessionId, updatedAtMs, entries ordered by position (1 to n, each car once): position, carNumber, teamName, schoolName, laps, status (running, inPit, stopped, retired, disqualified, notStarted), and optionally lastLapMs, bestLapMs, gapToLeaderMs or gapToLeaderLaps, intervalMs, pitStops, fuelStops (refuels, since BAJAOVRLAY-22; the simulator writes it equal to pitStops because in its model every pit stop is a refuel). lastLapMs and bestLapMs are above 0 (a 0 lap time is a placeholder). The gap rule (gate 2 of PR #16, João): a gap is optional, the source may not know it; when present it is the right kind, measured from the leader, which is position 1 whatever its status (a source ranking a retired car with the most laps first measures from it): none on the leader, gapToLeaderMs only on a car on the leader's lap, gapToLeaderLaps only on a lapped car and equal to the laps it is behind, never both, and none on a car with more laps than the leader. A car still in the race (running, inPit, stopped) never has more laps than the nearest car still in the race ahead of it; retired, disqualified and notStarted cars may sit out of lap order. The leader carries no interval; any other car may carry one, as the source measures it.
- standings: scope (overall or a sessionKind), updatedAtMs, entries ordered by rank (ties share a rank): rank, carNumber, teamName, schoolName, points. As built by BAJAOVRLAY-24 the score's parts are the source's own, not session kinds (the real overall score is PROJETO, DINÂM., ENDURO, 4X4, SEG. and PEN.): optionally scoreParts ({ partId, label }, in display order, the label pt-BR as the source names it) and, on an entry, pointsByPart (partId to number; a part left out is unknown and shown as "—"), a key that names no listed part refused; pointsByEvent is gone, and an old recording that carries it replays with the field dropped. An entry may be isDisqualified (optional; left out means not disqualified): it has no rank and comes after every ranked entry, and each of the first ten rows offers it as a yes-or-no path.
- brackets (a draft until BAJAOVRLAY-25 checks it against the Baja app's tournament table): sessionId, updatedAtMs, rounds (name, matches: matchId, carA and carB each carNumber, teamName, schoolName and optional timeMs, optional winnerCarNumber, which must be carA or carB).

- incidents (BAJAOVRLAY-44): sessionId, updatedAtMs, entries in the source's order: incidentId (the source's own, stable; listed once), carNumber, teamName, schoolName, kind (penalty, warning, incident), reason (pt-BR), and optionally penaltyText ("+30 segundos"), lap and atMs. Its whole list is bindable (incidentsEntries) and its fields mappable by a flex source. The simulator draws a few penalties and warnings over the race (one per 30 minutes, the first a penalty). The positions entries gain bestLapNumber (optional, from 1), bindable and mappable.

Gap precision (BAJAOVRLAY-40, João on BAJAOVRLAY-18): the shapes keep gaps in integer ms, but a gap shown on any screen is written to the tenth of a second or to the second, cut and never rounded ("+12,3 s" for 12 399 ms), and never to the ms, because Baja's timing records line passes with limited accuracy. Today that is formatGapToLeader on the Fontes page; the on-air formatting of BAJAOVRLAY-20/21 follows the same rule. Lap times keep their ms on the Fontes page ("4:38.293"), a diagnostic screen (João's ruling at gate 2 of PR #17), while its gaps stay at the tenth.

validateDataShape(shapeKey, payload) checks one payload and names the first problem by path in pt-BR; unknown extra fields are dropped. The "describe" of the original design became listBindablePathsOfShape(shapeKey), per shape and not per adapter, hand-listed with pt-BR labels ("Posições › 1º colocado › Equipe"; standings by row, "Pontuação › 1ª linha › Equipe", since tied teams share a rank) for BAJAOVRLAY-20's picker. As built by BAJAOVRLAY-20 every path also carries its value type, the session lists its whole clock (clock, the clock group) before the clock's fields, and the positions list a car chosen by its number (entryOfCar.<field>, with carNumber in the binding) after the whole list. samples/ holds realistic payloads that are also the test fixtures.

The adapter interface (apps/server/src/modules/dataSources/adapters/dataSourceAdapter.ts): kind, configSchema (the shared schema of that kind), listProducedShapes(config), pollOnce(config, context), which resolves to { shapes } or throws, and an optional prepareForPolling(config), which starts any slow preparation (a replay reading its recording) and returns at once; the poller calls it when a source's loop starts and when its config changes, so no poll pays for it. The context holds readCurrentTime and an AbortSignal that fires at the timeout, which every adapter must honour (pass it to fetch, or stop waiting; gate 2 of PR #16 and its re-check). A poll called off while its adapter is still preparing rejects with StillPreparingForPollingError, recorded with its own message ("Carregando a gravação…") instead of "Tempo esgotado". The framework checks every shape and accepts all or none. The kinds built are simulator (a deterministic enduro, a pure function of seed and simulated time; its README says what it models and that it is not the real scoring), replay (§7 rule 8) and, since BAJAOVRLAY-40, httpJson, the flex source (below). The recorder is one framework piece for every kind, not one per adapter. The poller runs one loop per source that is on: it polls, waits pollIntervalMs after the poll settles (a fixed rhythm, no backoff; never two polls of one source in flight), times a poll out after min(pollIntervalMs, 10 s), and sends every result through recordDataSourcePoll as the source's own actor; it never writes state itself. It reads the current source from the store at each poll, so an edit applies from the next one, and drops the late answer of a source turned off or deleted. A stale watch per loop marks a source stale ("Sem dados novos há N s.") when no good poll came within staleAfterMs, which also catches an adapter that ignores its signal. It logs a warning per failed poll and an info line when a source goes stale or recovers.

The flex source, as built by BAJAOVRLAY-40. Instead of one hand-written adapter per source (a sheet, another timing system, a committee's JSON file), the httpJson adapter (apps/server/src/modules/dataSources/adapters/httpJson) reads any JSON API with the requests and the mapping of its config (§4). Each poll fetches every request at once with Node 22's built-in fetch and the poll's AbortSignal, reads each body as JSON, and hands the responses to applyFlexMapping with the poll moment from the context's readCurrentTime. A source never half-succeeds: one request failing fails the whole poll, and there is no retry inside a poll, because the poller's fixed rhythm is the retry. Redirects are not followed, so a header holding a token never goes to an address the operator did not type. The pt-BR errors are "Tempo esgotado" (the poller's own) when the signal fires, "A fonte respondeu 503 (Service Unavailable) em classificacao" for an answer outside 2xx, "A resposta de classificacao não é JSON válido", "A resposta de classificacao passou de 5 MB" for a body over the cap (read as a stream and stopped there, so a runaway endpoint cannot fill the server's memory) and "Não consegui conectar a <host> (classificacao): <reason>" for a network failure. Which hosts it may fetch is BAJAOVRLAY_SOURCE_ALLOWED_HOSTS (above, with the secrets): with the list set only its hosts, with it unset any host but with no variable's value sent. There is no separate filter on private or local addresses, because the timing system on the event LAN is the main case.

The mapping (packages/shared/src/flexMapping) is pure code, so the server's adapter and the control page's "Testar" panel run the same applyFlexMapping on the same input. Its rules:

- One mapping per produced shape, each shape at most once per source: session (fields, the rules of its canonical fields), positions and standings (entriesPath, the path to the array in the response; entryFields, the rules applied to each element; and fields, the top-level rules such as sessionId, updatedAtMs and standings' scope). Brackets cannot be mapped yet: it is a draft shape (BAJAOVRLAY-25), and a nested rounds-of-matches mapping would double the mapping code for a shape no source sends. A standings team's pointsByPart is mapped from one list per team, each part { label, value } (the label is the part's id), and the standings' scoreParts is built from every label met; isDisqualified is an entry field like the others (BAJAOVRLAY-24).
- One response per shape, and no joins. A shape's rules read the one request its requestId names. Positions and standings need teamName and schoolName on every entry, so a source whose timing endpoint gives car numbers only, with the names in another endpoint, cannot be mapped: a join across requests would be a second mechanism to read and test, and for the main source the fix is upstream (BAJAOVRLAY-18's endpoint spec asks that every entry carry car number, team and school). The entity library (BAJAOVRLAY-19) may later fill names by carNumber; that is its decision.
- A field rule is a targetField (a canonical field from listMappableFieldsOfShape, hand-listed with pt-BR labels like listBindablePathsOfShape, nested with a dot for clock.referenceTimeMs) and exactly one source: fromPath, read from the response or from the entry, with an optional transformId and its transformParameters; constantValue (sessionKind "enduro", or a scope the source does not send); fromListOrder (entries only, the 1-based place in the array, for a source that sends its list in order but no position or rank); or fromPollMoment (the poll's moment on the server's clock, for a source with no updatedAtMs). One transform per rule, no chains.
- A path is dot-separated keys and numeric indices (dados.corrida.carros[3].equipe), parsed by hand, with no wildcards, filters, recursion or functions; a key holding a dot or a bracket, and a response whose top level is a list, cannot be read. Every path is checked when the config is saved.
- A path that is missing, or holds null, leaves the field out (the source does not know); if the field is required, the canonical validation says so. A transform that refuses fails the whole poll, so no field is ever dropped silently because its value was unreadable. Unknown extra fields in the response are ignored.
- applyFlexMapping(mapping, responsesByRequestId, pollMomentMs) answers { ok: true, shapes } or { ok: false, problems }, each problem a pt-BR line naming the shape, the entry when there is one, the target field and the source path ("Posições › carro 7 (linha 3) › Última volta: não consegui ler "4:3x.293" em tempos.ultima"). It keeps the first 20 problems, so a mapping is fixed in one go, and the poll error stored on the source is the first one plus "(e mais N problemas)". The shapes then go through validateDataShape like every other adapter's, in recordDataSourcePoll; "Testar" runs the same validation, so what the operator sees there is what the poller accepts.

The sample route, POST /api/v1/data-sources/http-json/sample-request ("Buscar da fonte" on the flex source form), takes one request in the config's own request schema and answers { ok: true, status, body } with the parsed JSON, or { ok: false, error } with the same pt-BR errors as a poll. It runs the poll's fetch code with the same caps and a 10 s timeout, and reads BAJAOVRLAY_SOURCE_ variables on the server, so the page never sees a token. It is a read with no state change, so it is a REST route and not a command, and it writes no event-log row; it is in the OpenAPI like the other routes. On the page, "Testar" also takes a pasted sample, for an endpoint that is not up yet, and runs applyFlexMapping and validateDataShape in the browser; "Exportar configuração" and "Importar configuração" carry a tested config as JSON, which is how BAJAOVRLAY-18 will ship the Baja app's preset. packages/shared/src/flexMapping/examples holds a fictional timing system's response and its preset, which are also the test and e2e fixtures (pnpm serve:flex-example serves the response locally).

## 10. Stack, aligned with Paddock

Identical to Paddock unless listed under deviations: TypeScript strict, Node 22 LTS, ESM, pnpm workspaces; Drizzle; Zod at every boundary; /api/v1 with OpenAPI generated from Zod; shadcn/ui with semantic tokens; react-hook-form with Zod; Vitest and Playwright; structured logger with request_id, console.log lint-banned; i18n catalog (pt-BR only, see §18); module layout core plus modules, each module with schema.ts, service.ts, api.ts, index.ts; qualified cross-module imports; branches named like BAJAOVRLAY-12-rundown-reorder, one task = one PR, squash merge, CI gates.

Deviations, on purpose:

- SQLite (better-sqlite3 via Drizzle) instead of Postgres: single node, must run offline at the track, backup is a file copy.
- Vite + React for the control page instead of Next.js, served by a Hono server that also owns the WebSocket, REST, pollers and OBS control. The control page is 100% client-rendered realtime UI (Paddock's field-capture case, generalized) and Next has no native WebSocket path.
- Renderer is framework-free; graphics use Lit for the web components and GSAP for animation.

## 12. Readability law, a merge criterion for all code

The person reviewing this code is not its author and will not have an IDE open. Every rule below follows from that.

Naming. Names are sentences with the vowels left in: resolveItemFieldsIntoGraphicData, not resolve; isStale, not st. Abbreviations only for domain terms everyone here knows (OBS, WS, RPM). Booleans read as questions (hasLiveBindings). Functions are verbs, data is nouns.

Files. One responsibility per file, and the filename says which. Target 80 to 300 lines; under 40 lines probably belongs with its neighbour, over 400 means a second responsibility moved in. No utils.ts or helpers.ts grab-bags; generic helpers get a named home (lapTimes.ts, ordering.ts).

Folders. Folder = feature or concept, never top-level dumping grounds like types, hooks or services. Every package and every module folder has a 5 to 15 line README.md saying what lives there and where to start reading.

Comments. Explain why and what could go wrong, not what the line does. Every exported function has a 1 to 3 line doc comment stating its purpose and the non-obvious inputs. Any deliberate trade-off ("we keep the stale snapshot on purpose; a blank table on air is worse") is written next to the code, not in the PR.

Cleverness budget: zero. No conditional-type gymnastics, no generic abstractions with one call site, no metaprogramming, no clever one-liners. If a reviewer would need to run it in their head, rewrite it as steps with named intermediates.

Public surface. Each module's index.ts lists what it exports with a one-line comment each. Nothing else is importable from outside.

## 13. Testing policy

Tests are the primary review artefact. A PR is reviewed by reading its tests first; if the tests do not explain the behavior on their own, the PR is incomplete.

- Unit (Vitest): binding resolver, transforms, command handlers, layer replace logic, WS protocol codec, each data adapter's normalizer.
- Integration (Vitest with a real SQLite file): persistence round-trips, migrations, event log, snapshot and reconnect rebuild.
- Component (Vitest with Testing Library): generated item forms from real manifests, layer status panel, rundown reordering.
- Renderer (Playwright): OGraf lifecycle ordering against a fake graphic, reconnect rebuild, one screenshot per graphic with sample data.
- E2E (Playwright): open control, preview, take, live update from a replayed feed, clear.
- Chaos (scenario suite): data source down, stale, garbage payload; WS drop mid-take; two operators taking on one layer at once.

Test readability, written for a beginner. Paddock's law applies (sentence-style names, arrange-act-assert separated by blank lines, table-driven named scenarios, no clever generation, factories named for what they build), plus:

- Every test file opens with a plain-language header: what this module is for, what these tests prove, what they deliberately do not cover.
- Every test has a one-line comment above arrange, act and assert explaining in everyday words what is being set up, done and checked, even when it looks obvious.
- Table-driven scenarios have a comment per row saying why that row exists.
- Test data reads like the real thing (team 42, "Baja UFPR"), never foo, bar or x1.
- Assertions state the expectation in the failure message, for example: expect(result, 'the leader must be first after the pit stop').

Flaky test = bug; quarantine visibly, never delete to green. CI blocks merge on lint, typecheck or any test failure.

## 14. Deployment

- Between events: one Docker image (the server serves the control and renderer builds and the graphics), compose stack on TrueNAS via Portainer, behind the existing proxy. The SQLite file and media live on a dataset covered by the nightly dump script.

- Backups at the event: copy the data folder to a USB stick at every session break (a one-click action on the control page's admin route).

## 19. Decisions from M0 review (2026-10-09)

- A graphic's id is its folder name under packages/graphics (for example race-clock), which is also its URL path /graphics/race-clock/. The OGraf manifest id (baja-race-clock) is metadata only.
- The graphics slice is derived from the filesystem, never from operator state: it is refreshed from every packages/graphics/*/dist/*.ograf.json on every boot.
- New instances start in status loading; renderer acknowledgement that moves them to on-air is an M1 item (BAJAOVRLAY-12).
- clearLayer and clearAll remove instances immediately; clearAll ignores the persistent flag (it is the panic button).
- takeGraphic has a target field defaulting to program; a take replaces only the instance on the same layer and target.
- The eventLog slice carries the newest 200 entries; the table keeps everything.
- Protocol errors on the WebSocket are answered as commandResult errors; there is no separate error message type.
- Race clock: pre is a real sixth state (PRÉ-LARGADA, neutral band). load requires complete data and is called once per instance; unknown fields are refused with 400 and the previous data is kept. updateAction is accepted at any time after load, including off air. A countdown (remaining mode) rounds partial seconds up; an elapsed clock rounds down.
- A built graphic package with no known default layer is registered on the fullscreen layer (a take there cannot displace the bug, clock or lower third). M1 replaces this guess: each manifest declares its default layer in a v_baja vendor field, and fullscreen with a logged warning remains the fallback.

# 00 — Concept & Architecture

Design authority for BajaOvrLay. This file is authoritative between milestones: as-built changes are written into it in the PR that makes them. The Plane page of the same name (BAJAOVRLAY project, `personal` workspace) is the human-readable mirror, which João updates from this file at each milestone close. v0.1 rev 3 plus decision records §18–§19.

## 1. What this is

A stream-graphics system for Baja SAE Brasil live streams: an operator control page where graphics are configured, pre-programmed and queued, and a renderer page that OBS loads as a browser source and that plays the graphics on air. Graphics get their data from the Baja scoring system, from small databases we run ourselves (teams, people, sponsors, schedule), and from values typed in by hand.

The previous attempt failed on three fronts (functionality, control, looks), so this project starts from a written design and treats operator usability as the primary requirement. A stream at the track is run by volunteers under time pressure; anything that needs explanation on the day is a defect.

### Non-goals for v1

- A visual template editor. Graphics are authored in code by a developer; operators only fill fields and press buttons.
- CasparCG or SDI output, newsroom (MOS) integration, 24/7 unattended playout.
- Multi-tenant or public hosting. This runs on our LAN at the event and on TrueNAS between events.

## 2. Vocabulary

- Graphic: one on-screen element type (clock, lower third, standings table), packaged as an EBU OGraf graphic: a manifest, a web component and assets.
- Layer: a named slot in the output where at most one graphic instance is on air at a time (clock, lower-third, fullscreen, ticker, bug). Layers have a fixed z-order.
- Item: a prepared use of a graphic: which graphic, which layer, and a value or a binding for each field. Items live in a rundown or in a quick-fire panel.
- Binding: a field value looked up from a data source instead of typed (for example scoring.enduro.positions). A binding is either live (keeps updating while on air) or a snapshot (frozen at take).
- Rundown: an ordered list of items for a session, with a cursor for "next".
- Take, Clear, Next: put an item on air on its layer; remove what is on that layer; advance a multi-step graphic (or the rundown cursor).
- Preview: rendering an item off-air so the operator can see it before taking it.
- Instance: a graphic currently loaded in the renderer (previewing or on air), with the data it was resolved with.
- Data source: a poller that produces a normalized JSON snapshot: scoring, a sheet or CSV, the entity library. (Original wording; the data words as built in M2 are below.)
- Entity: a record in our own library: team, person (speaker, judge), sponsor, schedule slot.
- Macro: a named list of commands run as one button press (clock on, positions on, bug on).

The words as João confirmed them after the M1 walk (BAJAOVRLAY-36), and as the control page uses them:

- Graphic (gráfico): one installed OGraf package, the race clock for example; it has a schema and no data of its own.
- Item: a saved use of one graphic on one layer with its field values, kept for the next takes; its graphic never changes, its layer and values do.
- Rundown: the ordered list of items of a session, with the cursor on the next one.
- Shortcut panel (painel de atalhos): a tab of buttons in "Atalhos e macros"; each button is an item, taken ad hoc, never moving the cursor.
- Instance: one graphic on an output right now, on air (program) or in preview, with the data it shows; taking or previewing an item makes one, and it names that item.
- Layer (camada): a slot of the output, in z-order, holding at most one instance per output.
- Macro: a list of steps (take an item, clear a layer, clear all, wait) run in order by one press.
- Preview (prévia): the result, exactly what the screen will look like after the take: what is previewed, what stays on air, and the layers marked "vai limpar".
- "Editar item" changes an item, and so every take of it from then on; "Edição rápida" changes one instance, the one loaded with "Editar" from a Camadas row, and that change is a one-off ("alterado no ar") until the operator saves it into the item ("Salvar no item").

Everything on air or in preview comes from an item (BAJAOVRLAY-37). Items are what can go on air; "Edição rápida" only changes what is already up, and a graphic made on the spot is made as a new item ("Novo gráfico…", then "Salvar e disparar").

The data words as built in M2 (BAJAOVRLAY-17), and as the "Fontes de dados" page uses them:

- Canonical shape (forma canônica): what session, positions, standings or brackets look like inside BajaOvrLay (packages/shared/src/dataShapes, §8). Every source maps its data into these four, and graphics bind only to them, never to a source's own format.
- Data source (fonte de dados): something the server polls for race data, one of a few kinds; the server keeps its last good answer (its snapshot) and says whether it is late ("atrasada"). An adapter is the code that reads one kind of source and answers a poll with canonical shapes.
- Simulator (simulador): a source that produces a deterministic Baja enduro from a seed and the time since its start, so graphics are built and rehearsed with nobody typing data. Its teams are fictional and its scoring is not the real one.
- Recording (gravação) and replay (reprodução): a recording is a source's good answers written to a file while "Gravar" is on; a replay is a source that plays a recording back on today's timeline. A rehearsal is a show run against a replay (§7 rule 8).

## 3. Architecture

Four deployable parts, one repository, one Node process at runtime.

- Control page (browser) talks to the server over WebSocket and REST.
- Server (Node) holds the state store (in memory, persisted to SQLite), the data sources (pollers producing snapshots), the binding resolver (item fields plus snapshots become data for a graphic), OBS control (obs-websocket) and the REST API at /api/v1 with OpenAPI, used by Companion, Stream Deck and scripts.
- Renderer page (browser inside OBS) receives state from the server over WebSocket.
- Graphics (OGraf packages) are static files served by the server and loaded by the renderer.

### 3.1 The server owns the truth

The server holds the whole application state in memory and persists it to SQLite. Clients never hold state of their own; they send commands and receive state. Every command that changes something or is refused is appended to an event log (who, when, what), with one exception since BAJAOVRLAY-17: a routine data-source poll that leaves the source's health as it was writes no row (§4). This is the NodeCG "replicant" idea reimplemented in one module: a store of named slices, each validated by a Zod schema, each broadcast to every connected client when it changes (the slices of one change together, in one message, §4). Renderer connections are the one exception: they never receive dataSnapshots (§4).

Consequences:

- A control page refresh loses nothing.
- A renderer refresh (OBS reloading the browser source) re-requests the snapshot and rebuilds exactly what was on air.
- Two operators on two devices see the same thing at the same time.

### 3.2 The renderer is thin and dumb

A framework-free TypeScript page. One absolutely positioned container element per layer, stacked in z-order. It loads OGraf graphics as ES modules and drives them through the OGraf lifecycle (load, playAction, updateAction, stopAction, dispose). It has no logic about what to show; it mirrors the instances slice. Every dependency in the renderer is a frame-drop risk inside OBS, so it stays minimal.

### 3.3 Graphics are OGraf, nothing else

Each graphic is an OGraf v1 package with a JSON Schema for its data. That schema is what the control page uses to generate the item form; no hand-written form per graphic. Graphics receive resolved data only and never fetch anything themselves. Theme values (colors, fonts, logos) arrive as CSS custom properties that the renderer sets on the layer container.

As built in M1 (BAJAOVRLAY-14): the control page holds no code for any one graphic, and a test (apps/control/src/noGraphicSpecificCode.test.ts) fails if the race clock's id or its reference field is named outside the catalog and the tests. Both forms, the item editor's and "Edição rápida", are generated by features/schemaForm from the manifest's schema, which must be an object with properties. What it reads from each property: title is the label (the key when there is none), description the help text, default the starting value, required whether blank is refused, minimum, maximum, minLength and maxLength the limits. A string is a text input, with enum a dropdown whose option labels come from OGraf's gddOptions.labels (the enum value itself when there is none), with format date-time a date and time input sent as ISO 8601 text. An integer or number is a number input, with v_baja.unit ms a duration typed as mm:ss. A boolean is a switch. An integer with v_baja.role wallClock also offers the kind "Momento da entrada no ar" (takeTime), and starts on it in a new form. Every other shape (arrays, nested objects, oneOf and the like) is shown as read-only JSON and passed through untouched. The form checks itself with a Zod schema built from the same JSON Schema, for pt-BR messages that name the field; the server's check stays the authority. On the manifest itself the server, not the control page, reads v_baja.updateRule: the name of the rule every update of that graphic on air runs through (§4); the race clock names carryClockForward, and a graphic that names none has no rule. packages/graphics/README.md states the same for whoever writes a manifest.

### 3.4 The control page is a realtime console

React with shadcn/ui, fully client-rendered, fed by the WebSocket state stream. Three areas always visible on a desktop layout: rundown (left), preview and program monitor (center), quick-fire panel and layer status (right). Data-operator screens (entities, standings overrides, data-source health) are separate routes that work on a tablet.

## 4. State model

Slices, each a Zod schema in packages/shared. Field names below are the real ones to be used in code.

layers: id, name, zIndex, replacePolicy (one of out-then-in, cut, crossfade), persistent. Fixed list per theme; not operator-editable.

graphics: installed OGraf manifests plus our metadata: id, manifest, defaultLayerId, category, thumbnailUrl, defaultFields.

rundowns and items: Rundown has id, name, sessionLabel, cursorItemId. Item has id, home (a rundown or a quick-fire panel), order, graphicId, layerId, fields (a map from field key to FieldValue), autoOutAfterMs (optional), label, color, notes.

As built in M1: rundowns and items are two slices, persisted like the others. cursorItemId is the id of the "next" item or null. A rundown may also carry wasLastItemTakenAtCursor: the server sets it when the last item is taken at the cursor (the cursor is then on nothing because the rundown was played to its end) and takes it off as soon as the cursor is put on an item; left out means no. One rundown, "Sessão principal" (id sessao-principal), is seeded on the first boot and on a database that has none. Every item has a rundownId; quickFirePanelId arrives with the quick-fire panels. order is counted from 0 and the server keeps each rundown's orders as 0, 1, 2 and so on with no gaps. color is one of six semantic names (neutral, info, success, warning, danger, highlight). autoOutAfterMs is a whole number of milliseconds above zero; no auto-out is said by leaving it out.

FieldValue is one of:

- literal: kind 'literal', value
- binding: kind 'binding', sourceId, path, live (boolean), transformId (optional)
- entity reference: kind 'entity', entityType, entityId, attribute (sugar for a binding into the entity library)

- take time: kind 'takeTime', no value (added in M1 by BAJAOVRLAY-13)

As built in M1 the FieldValue schema is a discriminated union on kind with two members. literal carries a value that may be anything, null included, but must be present. takeTime carries nothing else (one written with a value is refused, not stripped): at the take the server resolves it to the wall-clock milliseconds of that take, the same moment as the instance's takenAt and the event-log ts, and the stored item keeps saying takeTime, so every take of the item stamps its own moment. The item editor stores a wall-clock field (an integer whose manifest property says v_baja.role wallClock, such as the race clock's referenceWallClockMs) this way for every new item, so a clock saved running counts from the take and not from the save; the operator may switch the field to a typed number. What the editor stores, as built by BAJAOVRLAY-14: one FieldValue per field of the generated form, literal for a typed value and takeTime for a field left to the server; a field left cleared is not stored for a new item, and clearing a field of a stored item stores a literal null (updateItemFields cannot remove a key), which the take then leaves out of the data. The resolver stays pure: it is handed the moment of the command and reads no clock. binding and entity reference join the union in M2. Until then a field of any other kind never reaches a take: a command carrying one is refused with INVALID_COMMAND by the command schema, and a stored items row holding one stops the boot. The resolver's own refusal, UNSUPPORTED_FIELD_KIND with a message that names M2, is a guard kept ready for M2; it cannot be reached through the server today, and literal and takeTime never get it.

The item and rundown commands, as settled by BAJAOVRLAY-13: createItem (rundownId, graphicId, layerId, fields, label, and optionally order, color, notes, autoOutAfterMs) puts the item at the end of the rundown, or at the given position with the items from there on moving down by one; the server makes the id. updateItemFields (itemId, and any of fields, label, color, notes, autoOutAfterMs) changes only what it carries: fields are merged key by key, autoOutAfterMs null removes the delay, and the rundown, graphic and layer of an item cannot be changed. Since BAJAOVRLAY-36 updateItemFields also takes layerId (the command keeps its name): the next take of the item uses the new layer, while an instance already on air from it stays where it is; the graphic still cannot change, and a graphicId sent is dropped by the command schema. deleteItem (itemId) removes the item and renumbers the rest. reorderItems (rundownId, orderedItemIds) takes the full list and is refused with ITEMS_NOT_A_PERMUTATION unless it holds exactly the rundown's items, once each. moveCursor (rundownId, itemId or null) is refused for an item of another rundown. takeItem (itemId) resolves the item's fields into data and runs the server's one internal take step (putGraphicOnOutput, which every take and preview ends in), always on the program output, and the new instance carries the item's itemId; an instance keeps its itemId even after the item is deleted. takeNext (rundownId) is a takeItem of the item at the cursor and is refused with RUNDOWN_CURSOR_EMPTY when the cursor is on nothing.

The cursor rules: the first item created in an empty rundown gets the cursor and no later create moves it; a take moves the cursor only when the item taken was the cursor item, to the item after it, or to nothing after the last item (it never wraps to the top), so takeNext always moves it on, while a takeItem of any other item (a row fired ad hoc) leaves the cursor exactly where it was, a cursor on nothing included; deleting the item at the cursor moves the cursor to the item that followed it, or to nothing; reordering keeps the cursor on the same item; a refused command never moves it.

When an item taken with takeItem or takeNext has autoOutAfterMs, the server sends a clearLayer for the item's layer after that delay, as the actor sistema:auto-out, unless the instance has left the layer first. Since BAJAOVRLAY-36 that clearLayer carries target program (the one optional field of clearLayer; without it a clear takes both outputs), so a preview prepared on that layer stays. An actor whose name starts with sistema: is the server itself (no connection is ever given that role) and may send only clearLayer, apart from the macro runner and watchdog (M1, below) and the data-source poller and recorder (M2, below); the authorize step refuses every other command from it with NOT_ALLOWED. The wait lives in memory only: after a server restart nothing is rescheduled and the item stays on air until it is cleared.

Transforms are a registry of named, pure functions (topN(6), formatLapTime, abbreviateUniversity), never free-form expressions. Readable, testable, no surprises on air.

dataSources, as built in M2 (BAJAOVRLAY-17), is three slices. dataSources (saved): id, label, kind (simulator or replay so far; later kinds such as the Baja app join the same list), config (the kind's own Zod schema in packages/shared/src/dataSources, which the page's forms and the server's adapters share), pollIntervalMs (500 to 60 000), isEnabled, isRecording, pollNowRequestedAtMs (optional), and status: lastAttemptAtMs and lastOkAtMs (optional), lastError (pt-BR text or null), consecutiveFailures, isStale, staleAfterMs (three poll intervals) and recordingError (pt-BR text or null). A source is stale ("atrasada") when its last poll failed, or when no good poll came within staleAfterMs; a source that is off is never stale, it is off. One source, "Simulador — Enduro" (id simulador-enduro, kind simulator, default config, every 2 s), is seeded off on the first boot and on a database with none. dataSnapshots (saved): per source, sourceId, receivedAtMs and shapes, the canonical shapes (§8) of its last good poll; a failure keeps it and marks the source stale, never blanks it (rule 4), and after a restart every source that was on comes back stale, with its snapshot when it has one, until its next good poll (unlike turning a source on, which marks it stale only when it has a snapshot). recordings (memory only, rebuilt at every boot from DATA_DIR/recordings/<sourceId>/*.jsonl): id (<sourceId>/<fileName>), sourceId, sourceLabel, fileName (the start moment in ISO 8601 with ':' made '-', .jsonl), startedAtMs, endedAtMs (null while recording) and snapshotCount. The bookkeeping is pure state, changed by the reducers; the recorder only mirrors it to disk. A restart closes every recording (no source comes back recording).

The data-source commands. createDataSource (label, kind, config, pollIntervalMs) makes a source, off, with an id the server makes; the config is checked by the kind's schema and refused with INVALID_DATA_SOURCE_CONFIG naming config.<path>, and the page may never set a timeline start (the server drops it). updateDataSource (sourceId, and any of label, config, pollIntervalMs) carries the stored timeline start over, so an edit does not restart a race; a simulator whose speed changed keeps its simulated moment, and a replay whose recording, offset or speed changed starts again from the top. deleteDataSource removes the source and its snapshot; its recordings stay. setDataSourceEnabled turns a source on (a simulator's race starts only when it never started, a replay starts from the top every time; error and failure count are cleared) or off (not stale, snapshot kept, recording closed). pollDataSourceNow stamps pollNowRequestedAtMs, which the poller sees and polls at once unless a poll is in flight. startRecording and stopRecording ("Gravar", "Parar gravação"); starting an already recording source and stopping one that is not are answered ok and change nothing; pollDataSourceNow and startRecording on a source that is off are refused with DATA_SOURCE_DISABLED, a replay naming an unknown or still open recording with RECORDING_NOT_FOUND, an unknown source with DATA_SOURCE_NOT_FOUND. recordDataSourcePoll (sourceId, result: ok true with shapes and receivedAtMs, or ok false with error and attemptedAtMs) is sent only by the poller: every shape is checked against its canonical schema in the reducer, and a bad, unknown or missing shape makes the whole poll a failure whose error names the path in pt-BR (a poll never half-succeeds); a good poll stores the snapshot, makes the source healthy and counts a line in its open recording; a failed one marks it stale and counts the failure, keeping the snapshot and lastOkAtMs; a poll for a source deleted or turned off a moment ago is answered ok and changes nothing. A good poll that repeats the stored shapes on a healthy source is a no-op: nothing is saved, logged or broadcast, and its timestamps are not written (the poller judges lateness from its own memory of the last good poll).

The actors: the poller of each source signs as sistema:fonte:<sourceId> and may send only recordDataSourcePoll for that same source; the recorder signs as sistema:gravador and may send only stopRecording, which it does with a failureMessage when a write to the file failed (the source shows it as recordingError and keeps polling); operators and renderers may never send recordDataSourcePoll.

The event-log exception: a poll every two seconds would bury the operator's history (the eventLog slice keeps only the newest 200 rows), so recordDataSourcePoll writes an event-log row only when the source's health changes: isStale flips (the source goes stale or recovers) or the lastError text changes (an invalid payload is logged the first time it appears, not every poll). Every other poll saves its slices with no row. Operator commands, the recorder's stop included, are logged like any other command (an accepted command that changes nothing writes no row, as since 2026-10-10), and a logged poll row carries the whole command, shapes included, like any other row.

Renderer connections (/ws?role=renderer) never receive dataSnapshots: their hello carries it as an empty list and no later message carries it (apps/server/src/core/ws/slicesHiddenFromRenderers.ts), because graphics get resolved data only and a 60-car snapshot every two seconds is a frame-drop risk in OBS. The filter saves the renderer work and keeps nothing secret: the control page's monitor frames connect as operators, GET /api/v1/state returns every slice, and the logged poll rows in eventLog carry shapes. GET /api/v1/data-sources/{sourceId}/snapshot returns one source's snapshot.

overrides: sourceId, path, value, reason, setBy, setAt. Operator-typed values that win over the source until cleared. Shown as a badge everywhere the path appears.

instances (what the renderer mirrors): id, layerId, itemId, target (program or preview), resolvedData, currentStep, status (one of loading, ready, on-air, stopping, failed), statusDetail (optional; why a failed instance failed, as the renderer reported it), takenAt, fieldsChangedOnAir (optional; see below). A new instance is loading until a renderer reports it on-air or failed, and an on-air instance becomes failed if a renderer reports a failure afterwards; a failed instance stays in the slice until it is cleared or replaced, never removed on its own.

entities: tables for teams, people, sponsors, scheduleSlots. Teams carry number, name, university, city, logo, car photo. Sponsors carry tier and roll weight.

theme: semantic tokens for the on-air graphics (brand primary color, display font, logos, event name and year). One active theme.

macros: id, label, commands (a list of Command).

As built in M1 (BAJAOVRLAY-16): an item has a home instead of a rundownId, either a rundown (kind rundown, rundownId) or a quick-fire panel (kind quickFire, panelId), and its order counts within that home; items stored with rundownId are converted at boot and written back once, and a stored item with no home stops the boot. The slice quickFirePanels holds id, name, order; the panel "Atalhos" (id atalhos) is seeded, a panel with items or the last panel cannot be deleted, and createQuickFirePanel, renameQuickFirePanel, deleteQuickFirePanel and moveItemToHome (itemId, home, order; also how buttons are reordered) change them. A panel item is ad hoc by definition: it never gets or moves a rundown cursor, and moveCursor refuses it. A macro is id, label, color and steps, each step one of takeItem (itemId), clearLayer (layerId), clearAll, or wait (ms, 1 to 10 000), saved with createMacro, updateMacro and deleteMacro. runMacro (macroId) records a run in the macroRuns slice (macroId, startedAt, currentStep, isStopRequested), which lives in memory only and is empty at boot; a server-side runner then sends each step through the normal command path as the actor sistema:macro:<macroId>, strictly in order, a wait delaying the next step, and advances or ends the run with its own two commands. A refused step stops the macro, and nothing earlier is undone: on-air state is never rolled back automatically. An endMacroRun the store fails to apply is sent again a second later until it goes through, so a fault never leaves every macro locked. While any macro runs, runMacro, and updateMacro or deleteMacro of the running one, are refused. An operator stops a run with stopMacro (macroId; "Parar"), which only sets isStopRequested on the run: the runner sends no step after the one in progress, a wait in progress is cut short because it puts nothing on air, and the run is ended with endMacroRun as usual; nothing is rolled back. stopMacro of an unknown macro is refused with MACRO_NOT_FOUND, and for a macro that is not running, or a run already marked, it is answered ok and leaves no trace. A watchdog started with the runner gives each run a limit of the sum of its waits plus 30 s and ends any run still listed at that moment with endMacroRun as the actor sistema:macro-watchdog, with a warning log line naming the macro and the limit; a run that leaves the slice calls its watchdog off, and the runner forgets a run ended by the watchdog. The macro actor may send takeItem, clearLayer, clearAll and its own bookkeeping; sistema:macro-watchdog only endMacroRun, of any macro; sistema:auto-out still only clearLayer; operators may send stopMacro but never advanceMacroRun or endMacroRun.

eventLog: append-only: ts, actor, command, payload, result.

### Commands, the only way state changes

takeItem, clearLayer, clearAll, nextOnLayer, previewItem, stopPreview, takePreview, updateItemFields, saveOnAirChangesIntoItem, reorderItems, moveCursor, runMacro, stopMacro, setOverride, clearOverride, setDataSourceEnabled, upsertEntity, importEntities. Each has a Zod input schema; each is validated, authorized, applied, logged and broadcast, in that order, in one code path. Since BAJAOVRLAY-17 the data-source commands are createDataSource, updateDataSource, deleteDataSource, setDataSourceEnabled, pollDataSourceNow, startRecording, stopRecording and the poller's recordDataSourcePoll (dataSources above), and a routine poll is the one command that may skip the "logged" step.

updateInstanceData (instanceId, data) changes an instance that is on air, or in preview, without replacing it: the fields in data are laid over resolvedData (top-level keys only), the result is validated against the JSON Schema in the graphic's manifest, and the instance keeps its id, so the renderer calls updateAction instead of taking the graphic off and on again. An unknown instance is refused with INSTANCE_NOT_FOUND; data the schema does not accept, in a take or in an update, is refused with INVALID_GRAPHIC_DATA and a pt-BR message naming the field.

As built in M1 (BAJAOVRLAY-14), the take step (the public command takeGraphic until BAJAOVRLAY-37, now the server's internal putGraphicOnOutput, handed graphicId, layerId, data, target, takeTimeFieldKeys and itemId) and updateInstanceData (instanceId, data, and optionally takeTimeFieldKeys) prepare the data in steps before that check, in this order. First the nulls: a top-level null means "no value", so a take leaves that key out of the data and updateInstanceData takes that key off the instance's resolvedData, which is how an optional field leaves the air; a null deeper than the top level is a value like any other. Then the stamps: takeTimeFieldKeys (a list of field names, empty when left out) names the fields the server fills with the command's own moment in wall-clock milliseconds, the same moment as takenAt and the event-log ts, replacing whatever the command sent for them, so a client never sends its own clock. Only a field the graphic's schema declares as an integer with v_baja.role wallClock may be named: any other key is refused with INVALID_GRAPHIC_DATA before anything is stamped, and a graphic without a schema accepts no stamp. Then, in updateInstanceData only, the update rule the manifest names in v_baja.updateRule, if any. Update rules are a registry of named pure functions (apps/server/src/core/store/updateRules/), like the transforms above and never free-form expressions: a rule is handed the data on air, the fields sent, the keys stamped, the keys cleared and the command's moment, and hands back the fields to write. The one rule so far, carryClockForward, keeps a race clock from jumping: when the time, the running switch or the mode changed and the reference moment was neither stamped nor sent with a new value, it writes the typed time, or else the time on screen at that moment (never below 0), together with that moment as the new reference; when the mode changed and no time was typed, the time written is the whole second the screen was showing (elapsed rounds down, remaining up), so the number on screen does not move at the press; the sum and the rounding are the graphic's own, kept once in packages/shared/src/clock. A manifest that names an unknown rule, or one whose fields its schema does not declare, is warned about at boot and every update of that graphic is refused with INVALID_GRAPHIC_DATA; it can still be taken. Then the no-change check: an updateInstanceData whose result equals the data already on air (no field sent, nulls only for keys that are not on air, or the values already on air sent again) changes nothing and leaves no trace: it is answered ok, and nothing is saved, logged or broadcast; a stamp writes the moment of the command and is therefore a change. Last the manifest's schema, on the whole result: a required field taken off is refused with INVALID_GRAPHIC_DATA. takeItem goes through the steps of a take with the keys of its takeTime fields as the stamp list, so an item whose takeTime field is not a wall-clock field of the graphic is refused at the take, and an item field stored as a literal null goes on air without that field. createItem and updateItemFields run the same check on the takeTime fields they carry and refuse such a field with the same message, so it is not stored either.

As built by BAJAOVRLAY-37, everything on air or in preview comes from an item. The public commands takeGraphic and previewGraphic are removed: their schemas are gone, so a client sending one is refused with INVALID_COMMAND naming type. Every instance the server makes carries the itemId of the item it came from; an instance stored without one (put on air by hand before BAJAOVRLAY-37) still loads at boot and can be updated and cleared, and Camadas names it "sem item". takePreview refuses a preview with no itemId with INSTANCE_WITHOUT_ITEM, a guard no command can reach since previews are dropped at boot. updateInstanceData works on preview instances as on program ("Atualizar prévia"), keeping the id and the itemId, so takePreview promotes exactly what was seen: a key it sends with a value and does not ask to stamp leaves the preview's takeTimeFieldKeys (a typed moment survives the take), and an edited automatic preview becomes manual. On an instance with an itemId it writes fieldsChangedOnAir: the instance's earlier list, plus each top-level key the operator sent (in data, a null included, or in takeTimeFieldKeys) whose value now differs from what the item stores now (a literal compared by content, a field missing on air equal to a literal null or to no field; a takeTime field differs whenever it was sent). A key the update rule wrote by itself is not listed, and no update takes a key off the list; updateItemFields takes off the lists of the item's live instances (program and preview) every field whose stored value it changed, a new take carries no list, takePreview carries the preview's list to program, and left out means nothing changed. saveOnAirChangesIntoItem (instanceId, wallClockFields: keepMoment or atTake, required) writes each listed field into the item as a literal of its value on air (a field missing on air as a literal null), except a field the graphic's schema marks v_baja.role wallClock with atTake, which is stored as takeTime, and takes the saved fields off the lists of the item's live instances; a clock is saved whole: when any listed field has a clock role (clockTime, wallClock, clockRunning, clockMode), all of the graphic's clock fields are saved, so a clock stopped on air (only the running switch listed) comes back at the time it was stopped at; it is refused with INSTANCE_NOT_FOUND, INSTANCE_WITHOUT_ITEM, ITEM_NOT_FOUND (the item was deleted) or NOTHING_CHANGED_ON_AIR, and only operators may send it. The answer to an accepted createItem names the new item: CommandOutcome and the WebSocket commandResult carry createdItemId.

As built in M1 (BAJAOVRLAY-36), the slices one state change changed reach a client as ONE WebSocket message: slice (name, slice) when one slice changed, which is only a refused command since that changes the event log alone, and slices (slices: the changed slices by name, each checked by its own schema; serverNowMs required) when several did, which is every accepted command, as it changes its own slices and eventLog. The renderer turns either into one delivery and the control page into one store update, so no client ever draws some slices of a change new and the others old (sent one per slice, "Prévia: limpar" on a previewed layer showed the program clock on the Prévia page for a moment).

As built in M1 (BAJAOVRLAY-14 follow-up), every hello, slice and slices message carries serverNowMs, the server's wall clock as the message is built. A renderer page and the control page each keep the difference between that and their own clock as the median of the last five samples, and readServerAlignedTimeMs (packages/shared/src/clock) hands back their own clock plus that difference; the race clock reads it instead of Date.now(), so a clock on air counts from the server's clock even when the OBS machine's clock is off. The difference is kept in one property of globalThis, because the renderer and each graphic are separate bundles. In "Edição rápida", for a graphic whose manifest names carryClockForward and marks its four clock fields with the roles clockTime, wallClock, clockRunning and clockMode, the untouched time field shows the time on screen, live; the form still holds the reference that is on air, so that shown time is never sent.

reportInstanceStatus (instanceId, status on-air or failed, detail optional) is how a renderer says what really happened on screen: it moves a loading instance to on-air or to failed, and an on-air instance to failed when a renderer reports a failure later. Any other report (a second on-air, anything about an instance that is already failed, or a late report about an instance that is no longer there, which is the normal end of a quick clear) changes nothing and is answered ok, not refused. It is the only command a renderer may send, and an operator may not send it (nor the macro runner's bookkeeping or recordDataSourcePoll, above); the authorize step refuses the rest with NOT_ALLOWED. The server's own actors, sistema:, may not send it, and send nothing but clearLayer apart from the macro runner, the macro watchdog, the data-source pollers and the recorder (each limited to its own commands, above). Until login exists a WebSocket connection is a renderer when it connects to /ws?role=renderer (its actor is renderer: followed by the connection id) and an operator otherwise (operador: followed by the connection id); the role is taken at its word until the LAN PINs of M4. Only the program output reports: the page OBS loads (/render/) connects as a renderer, while the program monitor on the control page frames /render/?monitor=1, which connects to /ws with no role and never sends instanceStatus. With no program renderer connected an instance therefore stays loading.

The renderer does not wrap that command in a command message. It sends the client message instanceStatus (type, instanceId, status, detail optional) after playAction resolves, or after an import, load or play that failed, and the server builds reportInstanceStatus from it and runs it through the same code path as every other command.

## 5. Binding resolution and live updates

1. On take, the resolver walks the item's fields: literals pass through; bindings read the source snapshot at the path, apply overrides, apply the transform; entity references read the entity table. Result: resolvedData matching the graphic's schema. A validation failure refuses the take with a readable message; never a half-rendered graphic.
2. While an instance is on air, every time a data source snapshot changes the resolver recomputes resolvedData for instances with live bindings and, if anything differs, the renderer calls updateAction with only the changed keys.
3. Snapshot bindings are resolved once at take and never touched again.
4. A stale source does not stop live updates from being attempted; it shows a stale badge on the instance in the control page. Operators decide whether to clear.

## 6. Renderer contract

- URLs: /render/program (all layers, 1920x1080, transparent background) and /render/preview with an instanceId parameter (one instance, embedded in the control page).
- Load a graphic: create the custom element inside its layer container, await load with data, then playAction to step 0.
- Replace on the same layer, per the layer's replacePolicy. Default out-then-in: stopAction on the old, dispose, then load and play the new.
- Clear: stopAction (animated), then dispose.
- Next: playAction with delta 1; when the graphic reports it reached its end, the server marks the instance stopped.
- Reconnect: request the full instances slice, dispose everything local, rebuild each on-air instance with skipAnimation true.
- Timing metadata from the manifest (actionDurations) is used by the control page to show "animating" and to sequence macros; the renderer only awaits the promises.
- Later, optional: expose the OGraf Server API over REST so third-party controllers can drive our renderer.

As built in M1 (BAJAOVRLAY-15) the renderer is one page, /render/, and its address says what it is. /render/ is the program output OBS loads: it draws instances whose target is program, connects as a renderer and reports each instance on-air or failed. /render/?monitor=1 draws the same and reports nothing (the control page's "Programa" monitor). /render/?target=preview draws only instances whose target is preview, connects without the renderer role and never reports, with or without monitor=1 (the control page's "Prévia" monitor frames /render/?target=preview&monitor=1). Only those exact values count, so any other address is the program output. A preview page is the same reconciler and player: the one difference is that a replace there is always the cut (new graphic loaded behind the old one, then swapped with skipAnimation), whatever the layer's replacePolicy; a first preview still animates in and a discarded one out. Preview is whole layers, not one instance: the /render/preview address with an instanceId was not built.

Since BAJAOVRLAY-36 the preview page shows the result, exactly what the screen will look like after the take. One function, selectInstancesForPreviewComposition (apps/renderer/src/previewComposition.ts), picks per layer the preview instance if there is one, else nothing if the layer is in the previewClearedLayerIds slice ("vai limpar"), else the program instance; a previewed layer never shows its program instance. The reconciler composes the previous and the next delivery with it and then diffs as before, so there is no second code path (operationsPerDelivery.ts keeps the previous delivery; a slices message is one delivery, so the instances and the markers of one change are composed together); the program page still draws program instances only and never reads the markers. A program instance the preview page shows gets the same updates as on air; a marker arriving takes the layer's graphic off with its out-animation, and one going away brings the program instance back with its in-animation.

Every ten seconds the server sends each client the message time (serverNowMs), and hello, slice and slices messages carry serverNowMs too; a page records each as a sample of the server's clock (§4), and a message without it gives no sample.

## 7. Operator experience, the rules

1. Nothing goes to air without being visible first. Preview is one click and is always the same pixels as program. As built in M1 (BAJAOVRLAY-15): the centre shows two monitors, "Prévia" and "Programa", always side by side and the same size, 480x270 at most and shrinking together (always 16:9) on a narrower window. previewItem (itemId, origin) puts an item on the preview output of its layer, one instance per layer, resolved and checked exactly as a take; stopPreview (layerId, or null for every layer) discards it; takePreview (layerId) sends what was previewed to program without resolving it again, stamping only its take-time fields anew, and moves the cursor as takeItem does. A row of the rundown, a shortcut button's menu and the item editor ("Salvar e prévia") each offer "Prévia", the lines under the Prévia monitor have "Tomar" and "Descartar", and a layer holding a preview is marked "em prévia". With "Prévia automática" on (the default, kept per browser), the item the cursor arrives on is previewed by the page that moved it: after a move by hand with the arrows or a click, and after a take sent from that page that moved the cursor on, so Space, Space is the operator's loop and each item is seen before it airs. Such a preview carries origin auto, and the server first discards every other preview that was itself automatic, on any layer; previews asked for by hand (origin manual: a "Prévia" button, Shift+Space, "Salvar e prévia") stay until taken, discarded or replaced on their own layer. Each preview instance records its origin (previewOrigin). Previews are scaffolding: they survive a reload of the control page and are dropped when the server restarts. Since BAJAOVRLAY-36 Prévia shows the result (§6), and a set is looked at and taken in one go: previewClearLayer (layerId) marks a layer "vai limpar" in the previewClearedLayerIds slice (in memory only, empty at boot) and removes its preview, a preview on a layer removes its mark, and so does any take on program there (takeItem, takeNext, a macro step, a promoted preview: the plan to empty the layer is stale), stopPreview, clearLayer and clearAll remove marks too, and takePreview of a marked layer clears that layer on program. takeAllPreviews promotes every preview (as takePreview, layers in z-order) and applies every mark in one state change, one event-log row and one broadcast, so OBS never shows half a set; it then settles each rundown cursor once: while the cursor item is one of the items it took, the cursor moves to the following item (past the last, it is left on nothing with wasLastItemTakenAtCursor), so the cursor never rests on an item just put on air whatever the layers' order; with nothing previewed or marked, or with any one layer that cannot be taken, it is refused and nothing changes. previewMacro (macroId) discards every preview and mark, then plays the macro's steps onto preview only (takeItem previews the item, clearLayer marks, clearAll marks every layer with something on program, wait is ignored), so Prévia shows the macro's end state and "Tomar tudo" lands it in one cut without the waits; runMacro, which keeps the waits, discards previews and marks first. On the page: "Prévia: limpar" on a Camadas row, "vai limpar" lines, "Tomar tudo" and "Descartar tudo" when two or more lines are listed, and "Prévia" in a macro's ⋯ menu. "Edição rápida" never puts anything new on the preview output; a loaded preview is changed in place with "Atualizar prévia" (rule 3).
2. One-press actions for the common case: take, clear layer, clear all, next. Keyboard: Space = take, Backspace = clear layer, Esc = clear all, Right arrow = next. As built in M1: Space is always "take the item at the cursor" (takeNext), also while the focus is on a button, which is then not pressed; the Right and Left arrows move the rundown's cursor one item forward or back without taking anything, and a click on a row's label puts the cursor on that row. Since BAJAOVRLAY-15, Space sends takePreview when the item at the cursor is the one in preview and takeNext otherwise, and with "Prévia automática" on the take is followed by a preview of the new cursor item (rule 1); Shift+Space previews the item at the cursor; Backspace only discards the most recent preview and does nothing when there is none, so no key clears a single layer: a layer on air is cleared with its "Limpar" button, and Esc clears all. Same actions exposed to Companion and Stream Deck via /api/v1.
3. Forms are generated from the graphic's schema with sensible widgets: a team field is a searchable picker over the entity library, a standings field is a source picker, a duration is a number with units. Required fields block take with a message saying what is missing. As built in M1 (BAJAOVRLAY-14): the widgets are text, dropdown, date and time, number, mm:ss duration and switch (§3.3); pickers over entities and sources come with M2. A required field left blank, an empty required text included, is refused with a pt-BR message naming the field; an optional field left blank, or emptied with its "limpar" button, has no value and reads "Sem valor". "Edição rápida" in the centre only changes what is already up: the one instance loaded with "Editar" (on air) or "Editar prévia" on a Camadas row, named in its header ("Editando: <camada> · <item> · No ar" or "Em prévia"). Its one button, "Atualizar" (or "Atualizar prévia" for a preview), sends updateInstanceData to that instance's id with only the fields the operator changed, null for a cleared one, so the graphic changes in place and a preview keeps its item. It never follows takes made elsewhere and never moves to another instance by itself; when the loaded instance leaves, is replaced or its graphic is no longer listed, one line says so, the typed values are dropped, and the panel has nothing loaded. With nothing loaded it shows "Use Editar numa camada para alterar o que está no ar" and "Novo gráfico…", which opens the item editor on the shortcuts panel the strip shows: a graphic made on the spot is a new item. The item editor offers "Salvar e disparar" and "Salvar e prévia" beside "Salvar item": the save first, then takeItem or previewItem of that item; a refused take keeps the save and shows why. A change made with "Edição rápida" is a one-off: the Camadas row shows "alterado no ar" (the changed fields in its tooltip; beside "em prévia" too, for a changed preview, information only) and "Salvar no item", off while its command waits, keeps it for the next takes, first asking about the clock's moment whenever a clock field is among the changes, since a clock is saved whole ("Continuar este relógio" keeps the moment, "Começar na entrada no ar" makes it the moment of each take). Every Camadas row names its item, "item excluído" when it was deleted, or "sem item" for an instance put on air by hand before BAJAOVRLAY-37, which alone offers "Salvar como item" (the instance stays "sem item": a new item is made each time). The item editor offers "Atualizar no ar" while its item is on the program output: it saves the item and then sends the changed typed values to the instance on air. No form carries a rule for one graphic: a clock on air that is stopped, started, turned around or given a new time does not jump because the server's carryClockForward update rule (§4) writes the reference, not because the form sends it.
4. The state of every layer is visible at all times (what is on it, since when, live or stale badge). No hidden state.
5. Undo the last take (re-take the previous item on that layer) and a clearly marked clear all are always on screen.
6. Macros and quick-fire panels cover "the ten things we do every hour"; the rundown covers the scripted parts (openings, podiums, sponsor blocks). As built in M1 (BAJAOVRLAY-16): the right column holds a tabbed strip, "Atalhos e macros", above the layers. Each quick-fire panel is a tab with a grid of buttons in the item's colour; a click (or the digits 1–9 on the tab shown) takes the item without moving the rundown cursor, and a right-click or "⋯" offers Prévia, Editar and Mover para rundown. "+ Atalho" opens the one item editor with "Onde" set to that panel. The last tab, "Macros", lists the macros (the digits run them), shows "Rodando N/M" while one runs ("Rodando" alone for a macro with no step) with a "Parar" button beside it (stopMacro; the badge reads "Parando…" until the run ends), and opens the macro editor (steps added, removed and reordered by drag). F1–F4 switch tabs, and P ("Parar") stops the running macro whichever tab is shown and does nothing when none runs. Every shortcut is one entry of apps/control/src/keyboard/keyboardMap.ts, which the hooks read and the "?" button in the header lists. The page's keys are left alone while the focus is in a text field, a dropdown, an open menu or a switch; Esc ("Limpar tudo") works everywhere except on the press that closes a menu or dialog.
7. Roles: producer (playout), data (entities, overrides, rundown prep), dev (graphics; not a UI role). Auth on the LAN is a per-role PIN.
8. Rehearsal mode: a data source can replay a recorded feed, so the whole show can be practiced with no scoring system running. As built in M2 (BAJAOVRLAY-17): rehearsal is a source of kind replay ("Reprodução") playing back a recording. "Gravar" on any source writes its data at that moment and then each good poll as one JSON line { atMs, shapes } to DATA_DIR/recordings/<sourceId>/<start>.jsonl until "Parar gravação", the source being turned off or deleted, or a failed write. A replay names an ended recording and a speed (1, 2, 5, 10, 30 or 60×), optionally a start offset, and whether to start again at the end ("Recomeçar ao chegar ao fim") or hold the last line; every time it is turned on it starts from the top. Each poll answers the latest recorded line at or before "start offset + time since turned on × speed", with every updatedAtMs moved to now and the session clock's referenceWallClockMs moved so a bound clock shows now what it showed at the replayed moment (between polls it runs at 1×, so a fast replay's clock jumps at each poll; a plain replay that has ended stops its clock).

## 8. Data sources

- Scoring system: REST endpoints on the Baja app (see §18). Poll every 2 to 5 s during sessions; normalized into positions, standings.overall, standings.EVENT, brackets.EVENT, session (state, clock, flags).
- Entities: SQLite tables in the server. CSV import plus UI editing; logos and photos stored under data/media.
- Sheet or CSV URL: HTTP poll. For things the committee already keeps in a sheet (schedule, speakers).
- Manual: overrides and literal fields. Always available, always visible as such.

Original design (superseded by the as-built paragraphs below): every adapter implements the same interface: a poll function returning a Snapshot, plus a describe function listing the paths it produces (the control page uses this to build the binding picker). Every adapter ships with a recorder (writes snapshots to disk with timestamps), and a shared replayer provides rehearsal mode.

As built in M2 (BAJAOVRLAY-17), the canonical shapes (packages/shared/src/dataShapes). Every source maps into these and graphics bind only to them. Times are integer milliseconds: durations such as lastLapMs, and moments such as updatedAtMs in ms since 1970 on the server's clock. Every entry repeats carNumber, teamName and schoolName (short form, "UFPR"), so a graphic never joins tables. Optional means "the source does not know", never a placeholder such as 0.

- session: sessionId, eventName, sessionName, sessionKind (enduro, acceleration, speed, traction, suspension, maneuverability, other), state (exactly the race clock's flag values: pre, green, yellow, red, checkered, finished; a test reads the manifest so they cannot drift), clock, scheduledDurationMs and lapsCompletedByLeader (optional), updatedAtMs. clock is clockMode (elapsed or remaining), referenceTimeMs, referenceWallClockMs and running: the race clock's own field names, clockMode and not the brief's mode, so session.clock is a ClockReading and a binding feeds the clock with no rename.
- positions: sessionId, updatedAtMs, entries ordered by position (1 to n, each car once): position, carNumber, teamName, schoolName, laps, status (running, inPit, stopped, retired, disqualified, notStarted), and optionally lastLapMs, bestLapMs, gapToLeaderMs or gapToLeaderLaps, intervalMs, pitStops. The gap rule: the leader carries no gap; before the leader has completed a lap nobody does (unknown); after it, a car on the leader's lap carries exactly gapToLeaderMs and a lapped car exactly gapToLeaderLaps, equal to the laps it is behind. No car has more laps than the car ahead, and an interval is measured at the car's own last lap, so only a car with a lap may carry one.
- standings: scope (overall or a sessionKind), updatedAtMs, entries ordered by rank (ties share a rank): rank, carNumber, teamName, schoolName, points, and optionally pointsByEvent (sessionKind to number).
- brackets (a draft until BAJAOVRLAY-25 checks it against the Baja app's tournament table): sessionId, updatedAtMs, rounds (name, matches: matchId, carA and carB each carNumber, teamName, schoolName and optional timeMs, optional winnerCarNumber, which must be carA or carB).

validateDataShape(shapeKey, payload) checks one payload and names the first problem by path in pt-BR; unknown extra fields are dropped. The "describe" of the original design became listBindablePathsOfShape(shapeKey), per shape and not per adapter, hand-listed with pt-BR labels ("Posições › 1º colocado › Equipe") for BAJAOVRLAY-20's picker. samples/ holds realistic payloads that are also the test fixtures.

The adapter interface (apps/server/src/modules/dataSources/adapters/dataSourceAdapter.ts): kind, configSchema (the shared schema of that kind), listProducedShapes(config), and pollOnce(config, context), which resolves to { shapes } or throws; the context holds readCurrentTime and an AbortSignal that fires at the timeout. The framework checks every shape and accepts all or none. The kinds built are simulator (a deterministic enduro, a pure function of seed and simulated time; its README says what it models and that it is not the real scoring) and replay (§7 rule 8). The recorder is one framework piece for every kind, not one per adapter. The poller runs one loop per source that is on: it polls, waits pollIntervalMs after the poll settles (a fixed rhythm, no backoff; never two polls of one source in flight), times a poll out after min(pollIntervalMs, 10 s), and sends every result through recordDataSourcePoll as the source's own actor; it never writes state itself. It reads the current source from the store at each poll, so an edit applies from the next one, and drops the late answer of a source turned off or deleted. A stale watch per loop marks a source stale ("Sem dados novos há N s.") when no good poll came within staleAfterMs, which also catches an adapter that ignores its signal. It logs a warning per failed poll and an info line when a source goes stale or recovers.

## 12. Readability law, a merge criterion for all code

The person reviewing this code is not its author and will not have an IDE open. Every rule below follows from that.

Naming. Names are sentences with the vowels left in: resolveItemFieldsIntoGraphicData, not resolve; isStale, not st. Abbreviations only for domain terms everyone here knows (OBS, WS, RPM). Booleans read as questions (hasLiveBindings). Functions are verbs, data is nouns.

Files. One responsibility per file, and the filename says which. Target 80 to 300 lines; under 40 lines probably belongs with its neighbour, over 400 means a second responsibility moved in. No utils.ts or helpers.ts grab-bags; generic helpers get a named home (lapTimes.ts, ordering.ts).

Folders. Folder = feature or concept, never top-level dumping grounds like types, hooks or services. Every package and every module folder has a 5 to 15 line README.md saying what lives there and where to start reading.

Comments. Explain why and what could go wrong, not what the line does. Every exported function has a 1 to 3 line doc comment stating its purpose and the non-obvious inputs. Any deliberate trade-off ("we keep the stale snapshot on purpose; a blank table on air is worse") is written next to the code, not in the PR.

Cleverness budget: zero. No conditional-type gymnastics, no generic abstractions with one call site, no metaprogramming, no clever one-liners. If a reviewer would need to run it in their head, rewrite it as steps with named intermediates.

Public surface. Each module's index.ts lists what it exports with a one-line comment each. Nothing else is importable from outside.

## 13. Testing policy

Tests are the primary review artefact. A PR is reviewed by reading its tests first; if the tests do not explain the behavior on their own, the PR is incomplete.

- Unit (Vitest): binding resolver, transforms, command handlers, layer replace logic, WS protocol codec, each data adapter's normalizer.
- Integration (Vitest with a real SQLite file): persistence round-trips, migrations, event log, snapshot and reconnect rebuild.
- Component (Vitest with Testing Library): generated item forms from real manifests, layer status panel, rundown reordering.
- Renderer (Playwright): OGraf lifecycle ordering against a fake graphic, reconnect rebuild, one screenshot per graphic with sample data.
- E2E (Playwright): open control, preview, take, live update from a replayed feed, clear.
- Chaos (scenario suite): data source down, stale, garbage payload; WS drop mid-take; two operators taking on one layer at once.

Test readability, written for a beginner. Paddock's law applies (sentence-style names, arrange-act-assert separated by blank lines, table-driven named scenarios, no clever generation, factories named for what they build), plus:

- Every test file opens with a plain-language header: what this module is for, what these tests prove, what they deliberately do not cover.
- Every test has a one-line comment above arrange, act and assert explaining in everyday words what is being set up, done and checked, even when it looks obvious.
- Table-driven scenarios have a comment per row saying why that row exists.
- Test data reads like the real thing (team 42, "Baja UFPR"), never foo, bar or x1.
- Assertions state the expectation in the failure message, for example: expect(result, 'the leader must be first after the pit stop').

Flaky test = bug; quarantine visibly, never delete to green. CI blocks merge on lint, typecheck or any test failure.

## 19. Decisions from M0 review (2026-10-09)

- A graphic's id is its folder name under packages/graphics (for example race-clock), which is also its URL path /graphics/race-clock/. The OGraf manifest id (baja-race-clock) is metadata only.
- The graphics slice is derived from the filesystem, never from operator state: it is refreshed from every packages/graphics/*/dist/*.ograf.json on every boot.
- New instances start in status loading; renderer acknowledgement that moves them to on-air is an M1 item (BAJAOVRLAY-12).
- clearLayer and clearAll remove instances immediately; clearAll ignores the persistent flag (it is the panic button).
- takeGraphic has a target field defaulting to program; a take replaces only the instance on the same layer and target.
- The eventLog slice carries the newest 200 entries; the table keeps everything.
- Protocol errors on the WebSocket are answered as commandResult errors; there is no separate error message type.
- Race clock: pre is a real sixth state (PRÉ-LARGADA, neutral band). load requires complete data and is called once per instance; unknown fields are refused with 400 and the previous data is kept. updateAction is accepted at any time after load, including off air. A countdown (remaining mode) rounds partial seconds up; an elapsed clock rounds down.
- A built graphic package with no known default layer is registered on the fullscreen layer (a take there cannot displace the bug, clock or lower third). M1 replaces this guess: each manifest declares its default layer in a v_baja vendor field, and fullscreen with a logged warning remains the fallback.
